## 各問題

### R1. LINE 側と dip 側の境界が、コードでは守られていない

**何が問題か**: HLD の 1 章の境界(LINE 側は業務の知識を持たず、dip とは MCP でだけ話す)が守られているのは、
エージェントの情報の流れだけです。Web サーバーは dip の業務ロジックと状態を直接使い、dip の画面と API の多くを持っています。
一方で `CONTEXT.md` は aica を「求職者の仕事探しを支える AI エージェント」と定義していて、LINE の検証環境という前提と
ずれ始めています。境界を守るのか、外すのかが決まっていないので、新しい機能をどちら側に置くかが毎回あいまいになります。

**根拠**:

- `line_runtime/server.py:45-46`、`:66` が `dip_mcp.logic`、`dip_mcp.profile`、`State` を import し、dip の状態を直接読み書きする
- `line_runtime/server.py:10-11` は「LIFF 画面と状態確認 API は本来 dip が持つ Web 画面なので、dip の State を直接使う」と書く。
  実際には LIFF 画面のほか、プロフィールの API(`:532-630`)、履歴書の保存(`:800`)、音声相談の結果の受け取り(`:721`)、
  プッシュの判定(`:344`)も Web サーバーが dip の関数を呼んで行う
- `line_runtime/runtime.py:30` と `line_runtime/voice_reply.py:15` も `dip_mcp.logic` を import する
- `line_runtime/runtime.py:398` の `CARD_KEYS` は dip の求人カードの形を知っている
- `dip_mcp/logic.py:42-43` は `resume_intake` を import する(dip が履歴書の読み取りの部品に依存する)
- `line_runtime/agent.py:23` の指示は「LINE 公式アカウントの AI アシスタント(AIモード)」、`CONTEXT.md:3` は aica agent

**重さ**: 再開の前。直すのではなく、どちらにするかを決めます。

**直し方の案**:

- 案 A(境界を守る): dip の画面と API(LIFF、プロフィール、履歴書の保存、音声相談の結果、プッシュの判定)を dip 側の
  モジュールに移し、LINE 側からは MCP か、dip の公開する関数 1 か所だけで呼ぶ
- 案 B(境界をエージェントに絞る): 守る境界を「エージェントは dip のツールを通してだけ事実を得る」と HLD に書き直す。
  Web サーバーが dip の関数を呼ぶことは認める。名前(`line_runtime`、`LINE_SIM_*`、`line_user_id`)は、触るときに aica に寄せる
- 推奨は案 B です。検証したいこと(dip の Prompt とツールだけで会話体験が決まるか)はエージェントの境界で足ります。
  案 A は R8 を一緒に解く場合に価値があります

### R2. イベントの受け付けが 2 つの API と評価に重複している

2026-10-11 のレビューの候補 2 です。今の main でも重複しています。

**何が問題か**: `POST /api/event` と `POST /api/event/stream` が、それぞれ入力の検証、プッシュの判定、stale の照合、
ターン数の上限、知らせ、`LineRuntime` の呼び出し、開いた記録を持っています。評価は Web サーバーを通らず、プッシュの判定と
アップロードの事実を自分で組み立てます。受け付けの決まりを変えるたびに 3 か所をそろえる必要があり、評価は本番の受け付けを
確かめていません。

**根拠**:

- `line_runtime/server.py:330-365`(JSON)と `:368-415`(NDJSON)が同じ手順を持つ
- 違い: stream は判定の行(`gate`)を出し、すべての例外を `error` の行にして例外の文を画面に返す(`:412-413`)。
  JSON は `ValueError` だけを 400 にする(`:358-359`)
- ターンを数える `try_take` は 4 か所にある(`:351`、`:398`、`:682`、`:783`)
- 評価は `evals/run.py:125-153` でプッシュの判定とアップロードを、`evals/scenarios.py:36-45` でアップロードの事実を組み立て直す

**重さ**: 再開の前。jyoka/tasks#162 と #163 で予定しています。

**直し方の案**: 受け付けの手順(検証、判定、stale、上限、知らせ、ターン、記録)を 1 つのモジュールにまとめ、JSON と
NDJSON はそれぞれの書き出しだけを受け持つ。評価も同じモジュールを呼ぶ(上限はかけない設定で)。

### R3. Resume Draft の形と個人情報の決まりが 3 か所にあり、実際にずれている

2026-10-11 のレビューの候補 1 です。今の main でも複製されていて、安全の振る舞いのずれも見つかりました。

**何が問題か**: Resume Draft の形が 2 つの `schema.py` に、電話とメールを消す `scrub_pii` が 2 つに、個人情報を見分ける
別の決まり(`has_pii`)が dip にあります。`has_pii` は全角の数字と長音記号のハイフンをそろえてから見ますが、`scrub_pii` は
そろえません。そのため、全角で書かれた電話番号は、履歴書の読み取り結果と音声の下書きから消えずに残ります。

**根拠**:

- `resume_intake/schema.py` と `voice_resume/schema.py` は同じクラスを持つ。違いは説明の文、`FORMAT_VERSION`(`1.0` と `1.1`)、
  `envelope` の `document_kind`、音声側だけにある書類の種類の関数(`voice_resume/schema.py:18-39`)
- `resume_intake/extract.py:41-45`、`:88-100` と `voice_resume/drafter.py:18-22`、`:37-48` が同じ `scrub_pii`
- `dip_mcp/data.py:29-78` の `PII_VALUE`、`fold_pii`、`has_pii`、`redact_pii` は全角をそろえる
- `dip_mcp/logic.py:1027` の `save_resume_upload` は、保存の前に弱い方の `scrub_pii` をもう一度かける
- `dip_mcp/logic.py:920-922` の `DOCUMENT_KINDS` は `voice_resume/schema.py` の写し
- 2026-10-11 に今の main で確かめた結果:

| 文字列 | `has_pii` | `scrub_pii`(2 つとも) |
|---|---|---|
| `連絡先 090-1234-5678` | 見つける | 消す |
| `連絡先 ０９０－１２３４－５６７８` | 見つける | 残る |
| `連絡先 090ー1234ー5678` | 見つける | 残る |

**重さ**: 再開の前。個人情報の守りが実際にずれています。jyoka/tasks#164 で予定しています。

**直し方の案**: 個人情報の決まり(そろえ方と型)を 1 つのモジュールに集め、読み取り、下書き、dip の保存が同じものを使う。
形は 1 つのモジュールにし、説明の文の違い(書いてあるまま / 本人が言ったまま)は読み取りと下書きの指示の側に置く。
`docs/design/resume-draft-schema.md` の「2 か所に複製」の記述も直す。

### R4. dip の時計が固定で、LINE 側の時計と違う

**何が問題か**: dip 側の「今」は `SIM_NOW`(既定 2026-09-23 12:00)に固定です。シナリオを再現するための作りですが、
本番のトーク画面でも同じ時計を使います。LINE 側(会話を続ける 30 分、ターン数の日付、費用台帳)は実際の時刻です。
本番のユーザーの記録(保存、希望の保存日、履歴書のアップロード、音声相談の結果、区分の切り替え)は、すべて同じ固定の時刻に
なります。90 日以内、30 日以内、3 日以内の判定も、固定の時刻から数えます。

**根拠**:

- `dip_mcp/data.py:5`、`:26`、`:184-185`(`now()` は `SIM_NOW` を返す)
- `dip_mcp/logic.py` は 11 行、`dip_mcp/profile.py` は 3 行で `now()` を呼ぶ(例: `logic.py:732` トークを開いた記録、`:953` 音声相談の結果)
- `line_runtime/server.py:174-176`(`clock()` は実際の時刻)、`line_runtime/quota.py` と `ledger.py` も実際の時刻

**重さ**: 再開の前。時刻に関わる機能(再訪、プッシュの間隔、履歴の期限)を足す前に決めます。

**直し方の案**: 固定の時計はシナリオユーザーと評価だけに使い、本番のユーザーは実際の時刻にする。たとえば `now()` を
ユーザーか `State` ごとに差し替えられるようにし、`SIM_NOW` は評価と開発者画面のシナリオユーザーにだけ効かせる。

### R6. 音声相談の費用が台帳に載らず、上限も効かない

**何が問題か**: 音声相談は、始めるときにターンを 1 つ数えるだけです。相談の長さに上限が無く、LLM、文字起こし、読み上げ、
web 検索の費用は費用台帳に載りません。ターン数の上限は「費用の暴走を防ぐ防波堤」(`quota.py:3`)ですが、音声には効きません。

**根拠**:

- `voice_resume/*.py` に費用台帳を書くところが無い(`ledger` の参照が無い)
- `line_runtime/server.py:682-685` は 1 回の相談で `try_take` を 1 回だけ呼ぶ
- `voice_resume/agent.py:88-157` の `AgentSession` に相談の長さの上限が無い。`voice_resume/livekit_token.py:19` の 5 分は
  部屋に入るトークンの期限で、相談の長さではない

**重さ**: 公開の前。

**直し方の案**: 音声ワーカーが使った量(LLM のトークン、音声の秒数、検索の回数)を `user_id` つきで費用台帳に書く。
相談の長さに上限(たとえば 10 分)を置き、長さに応じてターンを数える。

### R7. 個人情報を保存する範囲と期間が決まっていない

**何が問題か**: 文書は「個人情報を dip に保存しない」と書きますが、守っているのは決まった項目と値だけです。本人がトークに
書いた文と音声の文字起こしはそのまま保存し、期限なく残ります。音声ワーカーは本人が話した希望をログに出します。

**根拠**:

- `line_runtime/runtime.py:69-75` の `event_input` は本人の文をそのまま会話に入れる。会話を消すのは「すべて消す」と
  履歴書を消すときだけ(`runtime.py:239-260`)
- `voice_resume/outputs.py:33` 以降が文字起こしを `data/voice-resume/` に書く。消すのはプロフィールの操作だけ
- `dip_mcp/data.py:219-284` の dip の状態に、ユーザーを消す期限が無い
- `voice_resume/agent.py:79` が本人が話した希望(`stated`)を INFO のログに出す
- `docs/design/resume-draft-schema.md:12-13` は「個人情報を dip に保存しない方針」と書く

**重さ**: 公開の前。

**直し方の案**: 何を、どこに、どれだけの期間保存するかを HLD の 6 章に書く。会話、文字起こし、使われなくなったユーザーを
期間で消す。ログには値を出さず、有無だけを出す。

### R8. dip の状態が 1 つの JSON ファイルで、複数のプロセスが書く

**何が問題か**: dip の状態は全ユーザー分を 1 つの JSON にし、読むたびにファイル全体を読み、書くたびに全体を書き直します。
書くのは Web プロセス、その子の dip、音声相談ごとの dip の 3 種類のプロセスです。ファイルロックは同期の呼び出しで、
Web サーバーの非同期の処理の中でも呼ぶので、待つ間はほかの要求も止まります。ユーザーは増え続けます。

**根拠**:

- `dip_mcp/data.py:219-284`(`_lock`、`_read`、`_write`、`user`、`update`)
- 書くプロセス: `line_runtime/server.py:66`、`dip_mcp/server.py:26`、`voice_resume/dip.py:36-46`
- 非同期の処理から同期で読む例: `line_runtime/server.py:251-257`(`talk_open`)
- task-hub の教訓「1 つのファイルに書くのは 1 者だけ」(task-hub の `docs/lessons.md`)と合わない

**重さ**: 公開の前。知人の規模なら今のままで困りません。

**直し方の案**: ユーザーごとの行を持つ SQLite にする(会話と同じ仕組み)か、書くのを dip のプロセス 1 つに集める
(R1 の案 A と一緒に)。

### R9. 音声ワーカーが、Web プロセスと同じマシンにいる前提で作られている

**何が問題か**: 音声ワーカーは、相談ごとに dip を stdio の子プロセスとして起動し、`DIP_MCP_URL` を見ません。結果には
下書きのファイルのパスを入れ、Web サーバーはそのパスのファイルを消します。音声ワーカーと Web プロセスは、同じファイル
システムにいないと動きません。

**根拠**:

- `voice_resume/config.py:92-94`、`voice_resume/dip.py:36-46`(常に stdio)。`line_runtime/runtime.py:110-114` は `DIP_MCP_URL` を見る
- `voice_resume/advisor.py:652`(結果の `files`)、`line_runtime/server.py:521-529`(`_remove_voice_files`)

**重さ**: 公開の前。Render の 1 コンテナなら動きますが、分けるなら直します。

**直し方の案**: 音声ワーカーも `DIP_MCP_URL` を使えるようにする。結果にはパスではなく下書きの中身を入れ、ファイルの
後片付けは音声ワーカーか dip が持つ。

### R10. 本番の Web サーバーが、評価のパッケージと開発者画面を抱えている

開発者画面を閉じられるようにする。

### R11. LiveKit のブラウザ用ライブラリを、版を固定せずに CDN から読む

### R12. Web プロセスのメモリに状態があり、1 プロセスでしか動かない

**何が問題か**: ターンの排他、会話の番号、音声相談の待ち合わせ、読み取れなかったアップロードがプロセスのメモリにあります。
費用台帳は書いた行をメモリにも持ち続け、長く動かすと増え続けます。

**根拠**:

- `line_runtime/server.py:193-194`(`voice_ready`、`unread_uploads`)
- `line_runtime/runtime.py:123-126`(`_locks`、`_threads`、`_running`)
- `line_runtime/ledger.py:57`、`:69`(`rows` に足し続ける)

**重さ**: 後で。今は 1 プロセスで動かします(HLD の 7 章)。

**直し方の案**: 1 プロセスの前提を HLD に書いた(済み)。費用台帳はファイルに書くときはメモリに残さない。読み取れなかった
アップロードは dip の状態に置く。
