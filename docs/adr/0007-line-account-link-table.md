# LINE のユーザーと dip の会員を、LINE のアカウント連携で結び、連携の表から dip_id を引く

ADR-0006 までは、LINE のユーザーと dip の会員の対応は、`data/state.json` の 1 人の dict の `dip_id` の欄だった。値は `fixtures/users.json` から写したもので、シナリオのユーザーのほかに会員とつながる道が無かった。本番の LINE のユーザー(`l-…`)と Web の匿名ユーザー(`w-…`)は、いつまでも「dip ID と未連携の新規」だった。

2026-10-21 に、LINE の Messaging API の「アカウント連携」の公式の流れで結ぶことにした(ユーザーの依頼)。次のように決めた。

- **流れ**: 本人が「アカウント連携」と送ると、bot が LINE から linkToken をもらい(`POST /v2/bot/user/{userId}/linkToken`)、dip のログインの画面(linkToken つき)へのボタンを返す。本人が dip にログインすると、dip は nonce を作り、nonce と会員ID を結んで覚え、本人を `https://access.line.me/dialog/bot/accountLink?linkToken=…&nonce=…` に送る。LINE から `accountLink` の webhook(`link.result` と `link.nonce`)が来たら、nonce から会員ID を引き、連携の表に書く。「連携解除」で表から外す
- **連携の表**: `data/dip_accounts.db`(SQLite、`dip_mcp/accounts.py`)の `links`。鍵は aica のユーザーID(LINE なら `l-<ハッシュ>`、Web なら `w-…`)で、LINE の userId そのものは持たない(task 177 の決まり)。dip のツールが `dip_id` を引くのは `behavior.dip_id` の 1 か所のままで、中身をこの表に差し替えた。1 人の dict には `dip_id` を写さない(引くところを 1 つにする)
- **同じファイルに置くもの**: dip の会員のログイン(`logins`。パスワードはハッシュ)、nonce(`nonces`)、bot が出した linkToken(`link_tokens`)。本物では、ログインと nonce は dip のもの、linkToken の記録は bot のものだが、このシミュレーションでは bot も dip の Web の偽物も同じ Web プロセスにあり、連携の表を読むのは dip のツールなので、1 つにまとめた
- **nonce**: `secrets.token_urlsafe(32)`(256 ビット)。1 回だけ使え、10 分で切れる。使い終わり、期限切れ、`link.result` が ok でないときは連携しない。nonce を作ったときの linkToken を一緒に覚え、webhook のユーザーに bot が出した linkToken でなければ連携しない(別の linkToken との組み合わせ)。nonce は、結果によらず、届いた時点で使い終わりにする
- **ログイン**: PBKDF2-SHA256(塩つき、20 万回)。同じログインID で続けて 5 回まちがえると 15 分ログインできない(正しいパスワードでも)。数えるのはログインID ごとで、会員にいない ID も同じに数える。ID とパスワードのどちらがちがうかは言わない。無い ID でも同じだけハッシュの計算をする。答えの文、ロック、時間のどれからも、ID があるかを知られないためである
- **シナリオのユーザー**: 最初から連携済みとして入れる。`data/dip_accounts.db` を初めて作るときに、`fixtures/users.json` の `dip_id` を種として入れる。`State.reset_user` は、写し元(シナリオのユーザー)の連携を写す。開発者画面のブラウザごとのシナリオユーザーも、同じ会員と連携済みで始まる(ADR-0006 で残した「シナリオユーザーごとに会員を分けるか」は、分けないことにした。同じシナリオの要約を読む今の形を変えないため)。`State.reset` は連携の表を初期に戻す
- **会員の数**: 1 人のユーザーが結べる会員は 1 人。1 人の会員を、複数のユーザーが結んでよい(シナリオユーザーの写しがそうなっている)
- **Web の匿名ユーザー**: LINE の webhook が届かないので、開発者画面から始める。LINE の役(linkToken の発行と accountLink の画面)は偽物の LINE(`line_runtime/fake_line.py`)がして、accountLink の画面を開いた人が linkToken のユーザー(Cookie の匿名ID)なら、署名を確かめた後の webhook と同じ処理に渡す
- **解除**: 連携の表から外すと、未連携の扱い(要約を読まない、プッシュしない)に戻る。`dip_writes` の 1 件は、書いたときに連携していた会員(`dip_id`)を持ち、読むときは今の会員の分と、未連携の間に書いた分だけを重ねる。解除した後に前の会員の行動を重ねず、同じ会員につなぎ直せば、連携の間に書いた分がまた重なる(消すと、要約に入るまで読めなくなる)。ツールが書いている途中に解除されても、その 1 件は書いたときの会員のものなので、未連携の人には重ならない。「すべて消す」(`State.reset_user`)も連携を外す
- **会話の途中の連携**: つないだ・解除したことは、プロフィールを直したときと同じ知らせ(`profile_changes`)で、次の本人のターンの前にエージェントへ渡す。前に読んだ要約(「未連携」や前の会員の行動)を使わず、要約を読み直させるためである

## Considered Options

- 案 A(1 人の dict の `dip_id` に書く): 書くところは少ないが、nonce と linkToken とログインの失敗の数を置くところが別に要る。`state.json` はファイル全体を書き直すので、nonce を 1 回だけ使う決まりを、プロセスをまたいで守るのにも向かない
- 案 B(連携の表を SQLite に置く): 採った。nonce を使い終わりにして表に書くまでを 1 つのトランザクション(`BEGIN IMMEDIATE`)でできる。dip のツールの子プロセスと Web プロセスが同じファイルを読める
- 案 C(LINE の userId を鍵にする): LINE の公式の例ではサービスが userId を持つが、task 177 で userId は保存しないと決めた。webhook の userId からいつも同じ `l-…` を作れるので、鍵はそれで足りる

## Consequences

- 連携の始まりと解除は決まった文(「アカウント連携」「連携解除」)で、LLM を使わず、ターン数も数えない。リッチメニューのボタンが送る文を想定している。自由な言い方(「dip とつなぎたい」)はエージェントに渡り、連携は始まらない
- LINE で連携を始めるには `AICA_PUBLIC_URL` が要る(dip のログインの画面へのボタンに使う)。無ければ「いまはつなげない」と返す
- dip のログインの画面(`/dip/login`)は Cookie を使わない。会員はログインで決まる。ログインの失敗の上限は会員ごとなので、他人がわざとまちがえて、その会員を 15 分ログインできなくすることはできる
- 本番のユーザー(LINE、Web の匿名ユーザー)が連携した後も、時計は実際の時刻のまま(ADR-0004)。fixtures の会員の行動は `SIM_NOW` 時点の要約なので、実際の時刻から見ると、7 日の判定(応募フォームの離脱など)には入らない。傾向と 30 日の数は要約のまま読める
- 連携の表が増えたので、`data/` の古い `state.json` の 1 人の dict にある `dip_id` は読まれない。開発者の手元の古いシナリオユーザーは、シナリオを始め直すと連携済みに戻る
- nonce と linkToken はハッシュで持つ。表が読まれても、そのまま使えない
