# 守る境界を「エージェントは dip のツールを通してだけ事実を得る」に絞る

LINE 側と dip 側の境界は、HLD の最初の版では「LINE 側は業務の知識を持たず、dip とは MCP でだけ話す」と書いていた。実際に守られていたのはエージェントの情報の流れだけで、Web サーバーと評価は dip の関数と状態を直接使っている(review-2026-10.md の R1)。境界を守るのか外すのかが決まっていないので、新しい機能をどちら側に置くかが毎回あいまいだった。

2026-10-12 に、守る境界を「エージェントは dip のツールを通してだけ事実を得る」に絞ると決めた。ここでの事実は dip の事実(求人、ユーザーの状況、業務の規則)で、web 検索や時給の相場のような外の情報は境界の外とする。音声アドバイザーも dip の事実は dip のツールで得ており、同じ決まりに合う(決定の言葉は「エージェント」だけで、音声アドバイザーへの当てはめは HLD での読み方)。Web サーバーと評価が dip の関数を呼ぶことは認める。判定と保存の決まりは dip の関数の中に置き、LINE 側で書き直さない。line-sim の頃の名前(`line_runtime`、`LINE_SIM_*`、`line_user_id`)は、その場所を触るときに aica の名前に寄せる。

検証したいこと(dip が書ける Prompt とツールの中身だけで、狙った会話体験になるか)は、エージェントの境界だけで確かめられる。画面と API まで dip 側に移しても、この問いの答えは変わらない。置き場所の基準は HLD の 1.1 に書いた。

## Considered Options

- 案 A(境界を守る): dip の画面と API(LIFF 画面、プロフィール、履歴書の保存、音声相談の結果、プッシュの判定)を dip 側のモジュールに移し、LINE 側からは MCP か、dip の公開する関数 1 か所だけで呼ぶ。dip の状態を書くプロセスを 1 つに集める(R8)ときには価値があるが、それだけのために今は移さない

## Consequences

- `line_runtime` が `dip_mcp` の `logic`、`profile`、`State` を import するのは、認めた形になる(HLD の 3.2)
- エージェントの指示(`agent.py` の LINE の共通ルール)とエージェントへの入力に、LINE 側で組み立てた業務の事実を足さない。足したい事実は dip のツールか dip の関数の結果にする
- イベントの入力の文言は LINE 側に置くが、書くのは何が起きたかと、画面に出したものを繰り返さない指示までにする。今のコードには会話の決まりを書いたところが 2 か所あり(`runtime.py` の `event_input` の読み取れなかったアップロード、`voice_event` の雇用区分)、触るときに dip の Prompt か playbook に移す(HLD の 1.1)
- R8 を案 A と一緒に解く道は閉じない。dip の状態を書くプロセスを 1 つにするときに、もう一度考える
