# 固定の時計(SIM_NOW)は、シナリオユーザーと評価だけに使う

dip 側の「今」は `SIM_NOW`(既定 2026-09-23 12:00)に固定されていて、本番のトーク画面のユーザーにも同じ時計を使っていた。LINE 側(会話を続ける 30 分、ターン数の日付、費用台帳)は実際の時刻なので、2 つの時計がずれる。本番のユーザーの記録はすべて同じ固定の時刻になり、90 日、30 日、3 日の判定も固定の時刻から数える(review-2026-10.md の R4)。

2026-10-12 に、固定の時計はシナリオユーザーと評価だけに使い、本番のユーザーには実際の時刻を使うと決めた。`SIM_NOW` は、評価と開発者画面のシナリオユーザーにだけ効かせる。LINE 側は今と同じく、どのユーザーにも実際の時刻を使う。

固定の時計は、fixtures の初期状態(「2 時間前に離脱」「9/19 に応募」など)を毎回同じ会話として再現するためのものだった。この目的はシナリオユーザーと評価にしか要らない。本番のユーザーに効かせると、時刻に関わる機能(再訪、プッシュの間隔、履歴の期限)が作れない。どの「今」をどこで使うかは HLD の 4.7 に書いた。

## Consequences

- 決めた時点(2026-10-12)のコードは、まだすべてのユーザーに `SIM_NOW` を使う(`dip_mcp/data.py` の `now()`)。実装は別のタスクで行う。HLD の 4.7 は「決まったこと」と「今のコード」を分けて書く
- 実装では、dip の `now()` をユーザーか `State` ごとに差し替えられるようにする。どちらにするかは実装のタスクで決める
- 実装の前に本番のユーザーについて保存した記録は、`SIM_NOW` の時刻のまま残る。直すかどうかは実装のタスクで決める
- Web プロセスと dip の子プロセスで `SIM_NOW` が分かれる問題(R21)は、シナリオユーザーと評価の中だけの問題になる
