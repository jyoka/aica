# dip のツールは状況の要約だけを読み、会話の中で書いたことは本人の分だけ重ねて読む

ADR-0005 で、dip の行動データを元データ(イベントのログ)と 1 人 1 行の状況の要約に分けた。task 180 の時点では、dip のツールはまだ `data/state.json` の 1 人の dict にある生の行動(`views`、`applications`、`saves`、`form_exits`、`contacts`)を読んでいた。

2026-10-21 に、dip のツール(`dip_mcp/logic.py`、`dip_mcp/profile.py`)が行動について読むのは要約だけにすると決めた(ユーザーの依頼)。元データは読まない。エージェントに渡るのも要約の分だけになる。

要約はバッチを回した時点の状況なので、そのままでは、会話の中で書いたこと(求人の保存、応募フォームの項目への答え、応募、プッシュの接触)が次のバッチまで読めない。保存した直後に「保存した求人はありません」と答えることになる。そこで次のように決めた。

- **書く**: 会話の中で書くものは、元データにイベントとして追記する。要約は次のバッチまで変えない。同じイベントを、その LINE のユーザーの dict の `dip_writes` にも残す
- **読む**: 要約に、`dip_writes` のうちまだ要約に入っていないイベントを重ねる(`dip_mcp/behavior.py` の `view`)。要約に入ったかどうかは、イベントの番号 `seq` と時刻を、要約の `through_seq` と `as_of` に比べて決める。入っていれば重ねない(二重に数えない)。次に書くとき、入った分を `dip_writes` から落とす
- **重ねるのは書いた事実だけ**: 保存と保存の取り消し、フォームの項目への答え、応募、接触を、要約の形のまま足し引きする。傾向(`tendency`)と、閲覧と訪問の数は重ねず、次のバッチを待つ。傾向は元データの閲覧と保存の一覧から数えるもので、要約には一覧が無いからである
- **フォームの項目への答え**は、新しいイベントの種類 `form_fill`(答えた項目名だけ。値は持たない)にした。`form_exit` を書き直すと離脱の時刻が答えた時刻に変わり、「2 時間前に離脱」が「0 時間前」になるからである
- **連携していない人**(`dip_id` が無い人)は dip に会員がいないので、元データには書かず `dip_writes` にだけ残す。本番のトーク画面の匿名ユーザーが求人を保存できるのは今と同じである。`dip_id` はあっても元データの会員に無い人(生成器の `--no-scenarios` で作った元データ、連携の表と dip のずれ)も、追記が外部キーで失敗したら同じく `dip_writes` にだけ残す。会員を勝手に足すと、dip に無い会員を会話の側から作ることになるからである
- **`as_of`**: エージェントに渡す要約(`get_user_conversation_summary`)と選考の状況(`get_application_status`)に `as_of` を入れる。dip の Prompt に、行動の事実は `as_of` 時点のもので、その後の行動は入っていないことがある(この会話で書いたことは入っている)と 1 行足した
- **期間の判定**: 要約の一覧は `as_of` から数えて 90 日、7 日で切ってある。読む側は、そのユーザーの「今」(ADR-0004)でもう一度絞る。30 日の閲覧と保存の数は数だけなので、`as_of` から数えたままにする。要約から来た保存を取り消したときは、その保存が `as_of` から数えて 30 日以内なら数を減らす(取り消しの時刻から数えると、今が `as_of` より後の人で減らない)
- **`dip_id` を引くところ**: LINE のユーザーIDから `dip_id` を引くのは `behavior.dip_id` の 1 か所だけにした。今は dict の `dip_id` を見る。認証のカードで、LINE の連携の表に差し替える

## Considered Options

- 案 A(書いた人の要約だけを、書いたときに作り直す): ADR-0005 で候補に挙げた。要約がいつも新しくなるが、書くツールが元データ(その人の全イベント)を読むことになり、「ツールは元データを読まない」を守れない。行動の多い人では書き込みが遅くなる
- 案 B(会話の中で書いた分を、本人の分だけ重ねて読む): 採った。ツールは要約と、自分が書いた分しか読まない。傾向がバッチまで変わらないのは、要約の時点の事実としてエージェントに伝える
- 案 C(要約を変えずに、Prompt で「保存したことはまだ出ない」と伝える): 実装はいらないが、保存した直後に保存が無かったことになる。プロフィール画面の「保存した求人」も同じになり、本人から見て壊れている

## Consequences

- 元データを読む関数(`EventStore.scan` など)を差し替えても、どのツールも動く(`tests/test_dip_summary_read.py`)
- シナリオの 5 人で、行動を読むツールの結果は task 180 の時点(main)と同じで、違うのは `as_of` を足したことだけである。会話の中で書いた直後の結果も、傾向と、傾向で決まる推薦の並びのほかは同じである
- 元データと要約は `State` と同じディレクトリに置く(`data/dip_events.db`、`data/dip_summaries.db`)。要約が無ければ、シナリオのユーザーの元データを入れて `SIM_NOW` で要約のバッチを 1 回回してから始める。要約は別の名前のファイルに作ってから置き換え、準備の途中の空の要約を別のプロセスに読ませない。評価とテストは実行ごとの一時ディレクトリなので、毎回この状態から始まる
- `fixtures/users.json` から行動を外した。シナリオのユーザーの行動は `fixtures/dip_events.json` だけにある
- `State.reset_user`(開発者画面のシナリオの開始、評価の準備)は `dip_writes` を消すので、読める行動は要約の時点に戻る。元データは追記だけなので、書いたイベントは残る
- 同じシナリオから始めた複数のユーザー(ブラウザごとのシナリオユーザー)は、同じ `dip_id` の要約を読む。会話の中で書いた分は本人にだけ重なるので、互いに見えない。ただし元データには同じ会員のイベントとして積もるので、開発者の手元の `data/` で要約のバッチを回し直すと、要約に混ざる。混ざった後は `State.reset_user` でもシナリオの初期の状況に戻らない(戻すには `data/dip_events.db` と `data/dip_summaries.db` を消す。次に使うとき作り直される)。シナリオユーザーごとに会員を分けるかは、認証のカードで連携の表を作るときに決める
- 要約の件数の上限がそのままツールに効く。応募済みとして推薦から外すのは新しい順の 30 件、プロフィールと `get_user_recent_applications` の応募は 90 日の 5 件、保存した求人は 10 件である。`save_job` が返す `saves_total` のために、要約に `saves_total`(保存している求人の数)を足した。保存が 10 件を超える人では、要約に載っていない古い保存の取り消しも元データに書く(載っていない求人を保存し直すと、次のバッチまで `saves_total` が 1 多く見える)
- 応募フォームの離脱は、要約に載る最後の 1 件だけを続きから再開できる
- 応募フォームにトークで答えた値は、どこにも保存しなくなった(前は state.json に値を持っていたが、読むところが無かった)
- 重ねるかどうかは、イベントの番号と要約の `through_seq` で決める。生成器の `--replace` で元データだけを作り直すと番号が振り直されるので、そのときは要約のバッチも回し直す
- 連携していない人の `dip_writes` は要約に入ることが無いので、書いた分だけ増える(シミュレーションの規模では困らない)
