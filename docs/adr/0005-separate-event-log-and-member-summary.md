# dip の行動データを、元データ(イベントのログ)と 1 人 1 行の状況の要約に分ける

dip の行動データ(閲覧、応募、保存、応募フォームの離脱、接触)は、`fixtures/users.json` と `data/state.json` の 1 人の dict に直接入っていた。鍵は LINE のユーザーIDで、`dip_id` はその中の欄だった。dip のツールは呼ばれるたびにこの dict を読み、90 日、30 日、7 日の判定と傾向の集計をその場で行う。

この形は、シナリオの 5 人なら困らない。本番の dip には、会員ごとに数か月分のアクセスログがあり、1 人で数百件になる。呼ばれるたびに生のログを数えると、ツールの速さが行動の量に比例する。エージェントに渡す事実の量にも上限が無い。会員の鍵が LINE のユーザーIDになっているのも、本番の形(dip の会員がいて、LINE の連携は後から付く)と違う。

2026-10-21 に、行動データを次の 2 つに分けると決めた(ユーザーの依頼)。

- **行動の元データ**: dip の会員(`dip_id` が鍵)と、行動のイベントのログ。イベントは追記だけで、書き換えも削除もしない
- **状況の要約**: 会員 1 人 1 行の、直近の状況の要約。定期の要約のバッチが、元データから全員分を作り直す。エージェント(dip のツール)が読むのは要約だけにする

置き場所は標準ライブラリの `sqlite3` にした。元データは `data/dip_events.db`、要約は `data/dip_summaries.db` で、ファイルを分けた。要約を読む側が元データを開かないことを、ファイルの境目で見えるようにするためである。追記だけの決まりは、`events` の表の UPDATE と DELETE を止めるトリガーで守る。

要約に入れるのは、今の dip のツールが使っている事実で足りるもの(閲覧、応募と選考の状態、保存、離脱、接触、傾向)と、訪問だけにした。件数と字数に上限を置き、1 行は JSON で 3,500 字を超えない。問い合わせのように、元データにはあっても今のツールが使わない事実は、要約に入れない。

要約は `as_of`(どの時刻までのイベントで作ったか)と `through_seq`(取り込んだイベントの最後の番号)を持つ。バッチの後に足したイベントは、次のバッチまで要約に入らない。要約が古いかどうかは、この 2 つで分かる。

## Considered Options

- 案 A(今のまま、1 人の dict に生の行動を持つ): 呼ばれるたびに集計する。データが小さいうちは単純だが、ツールの速さとエージェントに渡す量が、行動の量に比例して増える
- 案 B(元データだけを持ち、ツールが呼ばれたときに元データから集計する): 要約が古くならない。代わりに、ツールの速さが行動の量に比例し、本番の dip でアクセスログを会話のたびに数える形になる
- 案 C(要約を元データと同じファイルの別の表に置く): 1 つのトランザクションで済む。要約を読む側が元データの表も開けるので、ファイルを分けた

## Consequences

- この決定の時点(task 180)では、元データ、生成器、要約のバッチまでを作った。dip のツールは、まだ `data/state.json` の dict を読む。ツールの読み先を要約に変えるのは別のタスク(2/2)で行う。2/2(task 181)で決めたことは [ADR-0006](0006-tools-read-summary-and-overlay-own-writes.md) にある
- 要約は、バッチを回した時点の状況である。会話の中で起きたこと(保存、フォームの続き、応募)をすぐに要約に映すには、2/2 で、会話の中の書き込みを元データのイベントにし、要約との差をどう埋めるか(書き込んだ人の要約だけを作り直すなど)を決める
- 件数の上限で切るので、応募の多い人では、要約に載らない古い応募がある(`applied_job_ids` は新しい順に 30 件)。推薦から外す求人がこの 30 件だけになるので、2/2 で足りるかを確かめる
- 元データと要約の時刻は、シミュレーションの時計 `SIM_NOW` から見て作る(生成器とバッチの既定)。本番のユーザーの実際の時刻(ADR-0004)と、どう合わせるかは 2/2 で決める
