# シナリオごとの会話設計

aica(旧称 line-sim)の開発者画面と評価で使うシナリオ 16 件について、きっかけ・1通目・最初の1問・会話の段階・
出口・評価で確かめることを、シナリオごとにまとめる。語は [HLD の 10 章](../architecture/hld.md#10-用語)に従う。元の設計は 2026-09-24 にユーザーと決めたもの(jyoka/tasks#22)。
2026-09-27 に CRM 機能の削除(jyoka/tasks#56、PRD #54)に合わせて、新規ユーザー系の 5 件に再編し(7章)、再訪を2本に分けた(jyoka/tasks#57、8章)。
同日、相談のシナリオ 3 件を足した(jyoka/tasks#60、10章)。2026-09-29 に雇用区分と相談の深さを測るペルソナのシナリオ 6 件を足して 15 件にした(11章)。
2026-10-25 に、挨拶から 3 つの入口(音声相談・履歴書の読み込み・ゲーム)へ案内する決まりと、下書きのある再訪のシナリオ 1 件を足して 16 件にした(12章、会話の改善 (2/3))。

実際に動くものは次のファイルにある。この資料は「なぜその形か」と全体の見取り図を残すためのもので、細かい文言はファイルが正しい。

## 1. 前提: どのシナリオも AI 側の1通目から始める

Web 公開のプロダクトなので、トークを開いたことをイベントにできる。AI から先に話しかける入口は次の2つ。

| 1通目の出どころ | 誰が作るか | 送ってよいかの判断 |
|---|---|---|
| 初回訪問・再訪(トークを開いた)への挨拶 | エージェント | 常に挨拶する |
| dip のプッシュ(行動イベント) | エージェント(dip が渡す根拠の事実から) | dip の `push_trigger`(未連携・3日以内に接触済み・根拠が無い なら送らない) |

- **シナリオはすべて AI 側の1通目から始める**。ユーザーのメッセージを待って始まるシナリオは作らない。
- 入口 A(トーク)は本番の入口として Prompt に残すが、画面と評価のシナリオには無い。
- 1通目の後のやり取りは、その会話の続きとして扱う(入口の dip の Prompt は会話の途中で変えない。プロンプトキャッシュを保つため)。
- シナリオを始めるたびに、そのユーザーの dip の状態を fixtures に戻す。前のプッシュが接触として残ると、3日間プッシュが止まるため。

## 2. どのシナリオでも同じ会話の骨格

詳細は `baitoru_assistant.md`(dip の Prompt)。シナリオごとの設計は、この骨格のどこをどう使うかを決めたもの。

1. **理解**(ユーザーには見せない): `get_user_conversation_summary` で状況を読む。dip の要約は仮説として扱う。
2. **1問だけ聞く**: 選択肢はクイックリプライで最大4つ。必ず「今はいい」か「それ以外」を含める。
   こちらから話しかけるときは、最初の吹き出しで「なぜ今連絡したか」を根拠の事実で1文だけ伝えてから聞く。
3. **会話の段階**(ユーザーの3回目の返信までに入る。雇用区分ごとの値は `CONVERSATION_RULES`): 提案(求人を最大3件、理由つき)/ 相談(資料で答える)/ 支援(フォームの続き・応募状況)/ 待つ。
   提案の前にエリアが分かっていること。分からなければエリアを1問で聞き、この1問は3回目までの回数に数えない(13章)。
4. **出口**: `record_conversation_outcome` に propose / consult / support / wait を記録する。
   wait はユーザーが断ったとき(「今はいい」など)だけ。

## 4. シナリオごとの設計

### 挨拶で始まるもの(入口 V・R)

#### 1. 初回訪問(新規ユーザー)(`F-follow-new`)

| 項目 | 設計 |
|---|---|
| きっかけ | dip ID と未連携の人が、はじめてトークを開いた |
| 1通目 | 何ができるかを1文で伝え、3 つの入口(音声相談・履歴書の読み込み・ゲーム)を押せる形で出し、メニュー代わりの選択肢で聞く(12章)。行動履歴が無いので履歴には触れない。求人カードは出さない |
| 最初の1問と選択肢 | 求人を探す / まず相談する / 今はいい(「応募履歴を確認」は 12 章で外した。「使い方」は締めくくりの選択肢に残す) |
| 会話の段階 | まず相談する → 相談(playbook。10章)。求人を探す → エリアと仕事の希望をまとめて1問で聞く(13章) → 本人の言葉で `save_user_preferences` → `recommend_jobs` で最大3件(提案)。使い方 → FAQ の範囲で答える。今はいい → 待つ |
| 出口 | propose |
| 評価で確かめること | 1通目に「求人」と「相談」の選択肢がある(`expect_menu`)。窓口で使える入口が全部出ている(12章)。保存した希望が本人の発言どおり。提案まで進む |

#### 4. 再訪(希望あり)(`R-revisit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 未連携の人が、前にこのトークで希望(渋谷・日中・カフェ)を話していた。その人がトークを開き直した |
| 1通目 | dip の要約の `stated_preferences` を確認の形で1回だけ使う挨拶(例:「前回は渋谷・日中のカフェでしたが、今回も同じですか?」)。同じことを聞き直さない |
| 会話の段階 | 同じ + エリアを広げたい → 言い直した希望を保存し直して探す(提案) |
| 出口 | propose / wait |
| 評価で確かめること | 最初の返信で前の希望に触れる(`expect_uses_preferences`)。2通目以降で保存済みの項目(エリア・時間帯・職種)を聞き直さない。保存した希望が本人の発言か前の希望に基づく |

#### 5. 保存した求人について質問する(`Q-job-question`)

| 項目 | 設計 |
|---|---|
| きっかけ | カフェ・アパレルを閲覧しカフェを保存した人(連携済み)がトークを開き直した |
| 1通目 | 挨拶と、90日以内の行動から1つだけ確認の形で触れる1問(例:「最近はカフェのお仕事を見ていましたか?」)。閲覧した求人の名前や件数は挙げない |
| ユーザーの返事 | 保存したカフェ(カフェホール 渋谷道玄坂)について聞きたいと伝え、制服があるか、次にペットを連れて行けるか(求人の資料に無いこと)を聞く |
| 会話の段階 | `answer_job_question` が返す案件単位の FAQ(出典つき)で答える。資料に無いことは無いと伝え、推測で答えない |
| 出口 | consult / wait / propose |
| 評価で確かめること | 資料に無いことを作らない(事実性)。1ターン1問 |

#### 6. 再訪(行動履歴のみ)(`R-revisit-browsing`)

| 項目 | 設計 |
|---|---|
| きっかけ | このトークで希望を話したことは無いが、カフェ・アパレルを閲覧しカフェを保存した人(連携済み)がトークを開き直した |
| 1通目 | 挨拶と、90日以内の行動から1つだけ確認の形で触れる1問(例:「最近はカフェのお仕事を見ていましたか?」)。閲覧した求人の名前や件数は挙げず、求人カードも出さない |
| 会話の段階 | そう、探したい → 条件を聞いて(本人の言葉で保存し)探す(提案)。今はいい → 待つ |
| 出口 | propose / wait |
| 評価で確かめること | 1通目で最近の行動に触れる。触れるのは会話を通して1回だけ。1通目に求人カード・求人名・件数を出さず、職種も1つだけ(`expect_recent_activity`) |

### dip のプッシュで始まるもの(入口 D)

プッシュは、dip が `push_trigger` で送ってよいかを決め、根拠の事実を渡す。エージェントは、その事実にあることだけを書く。

#### 2. 応募フォームの途中離脱(`B-exit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 2時間前にコンビニ夜勤の応募フォームで離脱した(残り: 電話番号・希望開始日) |
| 根拠の事実 | 求人(`job_id`・`title`)、残りの項目、そのうち画面(LIFF)でしか受け取れない項目 |
| 1通目 | どの求人のフォームかを1文で伝え、どこで止まったかを1問で聞く |
| 最初の1問と選択肢 | 入力が面倒だった / 仕事内容が不安 / 条件が合わなかった / やめた |
| 会話の段階 | 入力が面倒 → `resume_application_form` で続きを案内。個人情報の項目は LIFF のボタンで(支援)。仕事内容が不安 → 資料で答える(相談)。条件が合わない → 条件を聞いて探す(提案)。やめた → 理由を聞かずに静かに終える |
| 出口 | support |
| 評価で確かめること | 個人情報をトークで受け取らない。入力画面のボタンを出す |

#### 3. 途中離脱で電話番号を書く(`pii`)

| 項目 | 設計 |
|---|---|
| きっかけ・1通目 | 2 と同じ |
| ユーザーの返事 | 台本どおり: 「入力が面倒だった」→「電話番号は090-1234-5678です。開始は来週からで」→「わかりました」 |
| 会話の段階 | 書かれた電話番号は記録せず、ツールの引数にも入れず、画面での入力を案内する |
| 出口 | support |
| 評価で確かめること | 電話番号を書かれたターンで入力画面のボタンを出す(`pii_test`)。どのツールの引数にも連絡先が入らない |

## 5. 評価で全シナリオに共通して確かめること

`evals/checks.py` がコードで判定する(LLM ジャッジは既定でオフ)。

- 1ターン1問。選択肢は最大4つで、質問には逃げ道(今はいい / それ以外)がある。吹き出しは80字以内(正社員は120字。`FORMAT_RULES`)。
- 求人は最大3件で理由つき。ツールやプッシュの根拠が返していない求人・金額・日付・件数を出さない(事実性)。
- 個人情報をトーク経由でツールに渡さない。
- 最初の返信は質問で終える。最後の返信を選択肢なしで終えない(「もう送らないで」の直後だけは例外で、
  「承知しました」で一旦終えるのが正しい。押しつけないため)。
- 断られていないのに wait を記録しない。「今はいい/送らないで」の後に質問や求人を続けない。
- 3ターン以内に会話の段階に入る(指標名は `branch_within_3`。探す前にエリアを聞く1問は数えない)。会話の段階の結果を記録する。期待した出口のどれかになる。
- エリアが分からないまま `recommend_jobs` を呼ばない(13章)。
- 挨拶の入口(12章): 初回訪問は窓口で使える入口を全部出し、再訪は 1 つだけ勧める。どちらも窓口で使えないものは出さない。

「今はいい」で会話が丁寧に終わる振る舞い(質問や求人を続けず、wait を記録して短く終える)は、
オフラインの台本テスト `tests/test_handle.py::test_ima_wa_ii_ends_the_conversation_politely` でも固定している。

## 6. 決めたことと経緯(2026-09-24)

- 画面の左パネルは「① ユーザーを選ぶ → ② 会話を始める(入口)」の2段だった。シナリオは明確なので、シナリオ単位の一覧1つにした。
- 評価のシナリオは 15 件から 11 件にまとめた(その後、PR #18 の `Q-job-question` を足して 12 件)。
- 画面の一覧と評価の一覧は同じファイル(`evals/scenarios.json`)にした。画面で試すものと評価で測るものを一致させるため。
- 入口 A(ユーザーが先に書き込む)だけで始まるシナリオは、評価専用にも残さない。挨拶だけのときにメニューを出す分岐は測らない。
- 「もう送らないで」の直後は、選択肢を付けずに「承知しました」で一旦終える。「最後の返信を選択肢なしで終えない」の例外にする。

## 7. CRM 削除に伴う再編(2026-09-27、jyoka/tasks#56)

Web 公開の v1(PRD jyoka/tasks#54)には LINE 公式アカウントの配信基盤が無いので、CRM 機能
(プッシュ配信〔新着・掲載終了・選考状況〕・休眠掘り起こし・配信停止/抑制の状態管理・crm_reply / follow イベント)を削除した。

- 削除したシナリオ: `P-new-match` / `P-saved-closing` / `P-app-status` / `C-dormant` / `stop` / `suppressed` / `F-follow-back`。
- 入口は follow / crm_reply をやめ、`visit`(初回訪問)と `revisit`(再訪)に統一した。`F-follow-new` は初回訪問に、
  `R-revisit` と `Q-job-question` は再訪起点に書き換えた(再訪の2振る舞い〔希望の確認 / 閲覧に1回触れる〕は
  旧 `R-revisit` / `F-follow-back` を継承)。
- `record_conversation_outcome` から stop と有効日数(配信抑制)を外した。「今はいい」「送らないで」に丁寧に応じて
  会話を終える振る舞いは残る(記録が wait になるだけで、停止処理は無い)。
- シナリオ集合が変わったので、旧 12 シナリオの評価結果とは evalkit の diff で直接比べない。

## 8. 再訪の2振る舞いを分けて測る(2026-09-27、jyoka/tasks#57)

- 入口は `visit`(初回訪問)と `revisit`(再訪)の2つ。再訪の挨拶は、プロフィールに保存した希望があれば確認形、行動履歴だけなら最近の閲覧に1回だけ触れる。
- 評価シナリオは、`R-revisit` を「再訪(希望あり)」に改名し、行動履歴のみの `R-revisit-browsing` を足した。
  `Q-job-question` も再訪起点だが、ユーザーが保存した求人を聞く流れなので、挨拶の振る舞いは `R-revisit-browsing` で測る。
- 評価の機械判定に「保存済みの希望を聞き直さない」「最近の行動への言及は1回だけ・羅列しない」を足した(`evals/checks.py`)。
- オフラインの台本テスト `tests/test_revisit.py`: 画面と同じ呼び方(シナリオ開始 → `/api/event/stream`)で初回訪問と再訪の挨拶が変わること、
  希望ありの再訪で差分だけ答えると提案とプロフィールが更新されること、行動履歴のみの再訪で閲覧への言及が1回だけで羅列しないこと。

## 10. 相談(v1 の相談モード、2026-09-27、jyoka/tasks#60)

> 2026-09-30(aica v2 の F): この節の「相談モード」は、雇用区分ごとの playbook(`dip_mcp/playbooks/`、
> `get_counseling_playbook`)に置き換えた。ヒアリングの順番と「合う職種が分からない → 職種を2〜3挙げる」は廃止し、
> 目的を聞いて掘り下げ、選択肢を履歴書と本人の発言から作り、「分からない」には掘り下げに戻る。今の決まりは
> [LLD の 4.9「相談の進め方(チャット)」](../architecture/lld.md#49-相談の進め方チャット)。以下は v1 の記録として残す。

何から始めればいいか分からない求職者向け。ADR-0003 のツール呼び出し型エージェントの中のモードとして、dip の Prompt
(`baitoru_assistant.md` の「相談モード」)のステージ指針と、入口の選択肢だけで実装した。別のエージェントやグラフは作らない。
ヒアリングの順(経験 → 興味 → 不安 → 生活の制約)は voice-resume の面談ステージ設計を流用した。

| 項目 | 設計 |
|---|---|
| 入口 | (a) 初回挨拶(と、履歴も前の希望も無い再訪)の選択肢「まず相談する」。(b) 会話中の迷いのサイン(「何から始めれば」「自分に合うのが分からない」)。特定の求人・条件への「考えます」「迷っている」は従来どおり迷いの点を1問聞く |
| ヒアリング | 1返信1問。経験 / 興味 / 不安 / 生活の制約(時間帯・週の日数・エリア)。答えが出ている項目は飛ばす。選択肢は答えの例を最大3つと「今はいい」 |
| 3ターン規則 | 相談モード中は「3回目の返信までに分岐」を適用しない。ヒアリングが終わるか本人が切り上げるまで続けてよい |
| 合う職種が分からない | 本人が話した経験と興味から、職種の一覧のうち2〜3つを理由つきで挙げ、どれが気になるかを1問で聞く |
| 保存 | 聞いたターンで `save_user_preferences`(既存の8項目: 経験は experience、時間帯・週の日数・エリアは time_band / days_per_week / area など)。興味と不安は項目が無いので保存しない(興味は提案の keywords に使う) |
| 出口 | ヒアリング後に「この内容で求人を見るか」を1問 → 保存した内容をそのまま `recommend_jobs` の条件にして提案(propose)。途中の「求人を見せて」はその時点の内容ですぐ提案。「今はいい」は提案なしで終え、1つでも答えていれば consult、何も話していなければ wait |

評価(`evals/checks.py`)は、相談モードのシナリオ(`consult_mode: true`)で次を見る。`branch_within_3` は規則を緩めているので測らない(None)。

- 初回の選択肢に「まず相談する」がある(`expect_consult_menu`)。
- 相談の入口(「まず相談する」か迷いのサインの発言)の返信は、求人を出さずにヒアリングの1問で始める。
- 本人が切り上げる(今はいい・求人を見せて・ありがとう など)前に `record_conversation_outcome` で相談を締めない。
- 相談の入口以降、「求人を見せて」のターンで求人を探す(即提案の指示はプロンプト上、相談モードだけ。非相談フローの
  「求人を見たい」に絞り込みの1問を返すのは違反ではない)。
- 相談で聞いた項目を保存した(`expect_saved_preferences`)。

全シナリオ共通のルールとして、この会話で保存した項目を後の質問で聞き直さない、も足した(照合は吹き出しの質問文の部分
だけ。まとめの平叙文で保存済みの値を復唱するのは聞き直しではない)。
台本テストは `tests/test_consult.py`。`C-consult-only` と `C-consult-switch` はユーザーの返信を台本(`script`)で固定している
(切り上げの一言を確実に起こすため)。`C-consult-propose` は模擬ユーザーの設定で動き、ヒアリングの分だけ長いので `max_turns` を 10 にした(aica v2 の E で、評価全体のターン上限 8 に合わせて 8 にした)。
実 API での基準計測はまだしていない(別 issue)。

## 11. 雇用区分と相談の深さを測るペルソナ(2026-09-29、aica v2 の E)

PRD `docs/prd/aica-v2-fulltime.md` の「評価と予算」。模擬ユーザーが全員新規・未経験寄りで、判定も形式しか見ていなかったので、
区分の切り替えと相談の深さを測るペルソナを足して15件にした。履歴書(`evals/personas/*.json`)も含めてすべて架空。

| シナリオ | 見るもの |
|---|---|
| `R-revisit-track` | 区分つきの再訪(`seed_track`)で、希望が無く行動履歴があるとき: 挨拶の1問に区分と最近の閲覧をまとめる(C の PR レビューの後続。入口R の Prompt にも書いた)。区分は聞き直さず、切り替えない(`expect_tracks: []`) |
| `T-career-fulltime` | 経歴の厚い正社員志望。「転職」で正社員へ切り替える。AI が履歴書の操作を出したら職務経歴書をアップロードし(`upload_resume`、出なければ `upload_by_turn` のターンで)、その後の1問を見る(UX 刷新 2/3 の PR レビューの後続) |
| `T-side-job` | 正社員の経理の職務経歴書がアップロード済み(`seed_resume`)でも、本人が「空いた時間でバイト」と言えばアルバイト・パート。履歴書から正社員と決めつけたら wrong_track |
| `T-student-first` | 初めてのアルバイト。目的(お金・経験)と不安(人見知り)の掘り下げ |
| `T-blank-parent` | 10年のブランク・扶養内・時間の制約。扶養の「壁」の金額(年収103万円など)は一般知識として作り話に数えない(A の PR レビューの後続) |
| `T-switch-to-fulltime` | アルバイト・パート → 正社員の2回の切り替えを、それぞれ本人の発言のターンで |

区分の切り替えは、シナリオの `expect_tracks` と、実際に区分が変わった `set_search_track` の呼び出しで機械判定する
(`evals/checks.py` の `track_expectations`)。期限は `turn`(何ターン目まで)か `on_said`(その発言に答えるターン)。
強い合図で期限より前に切り替えるのは正しい。模擬ユーザーが期待の発言をしなかった回は no_trigger として数えない。

相談の深さは LLM ジャッジ(`evals/judge.py`)の4項目を、根拠の発言つきで出す。形式の機械判定(1問・80字・会話の段階の期限)は
区分ごとに持ち(`FORMAT_RULES`)、正社員の値は F で決める。

あわせて、D・A の PR レビューで指摘された評価器の偽陽性・見逃しを直した(どれも負例・正例のテストつき):

- 聞き直しの判定: 「強みを活かせる求人を探しますか?」「年収の下限は500万円のままでよいですか?」「この中にやってみたいお仕事はありますか?」
  「この中で苦手な作業はありますか?」「勤務地を広げて探しますか?」は聞き直しではない。不安の問いの免除は、提案したターンと
  その後2ターンだけ(1通目で求人を出す再訪で、会話全体が免除にならない)。
- 自由記述の作り話: 発言に無い内容語が1つでもあれば違反(多数決をやめた)。漢字の複合語は発言の語に切り分けて照合する
  (「接客の経験」→「接客経験」)。内容語が残らない値は語ごとに照合する。目的は種類の名前(副業・生活費・転職 など)でまとめてよい。
- 金額: 月給から年収への換算(12か月分)は認める。扶養の「壁」の金額と、月・週の収入の目安(「月に約7万円」)は dip の事実の主張に
  数えない(手当・交通費・月給の話は数える)。本人が漢数字で言った額(「六百万」)は根拠にする。金額は給与の種類(時給・月給・年収)
  ごとに照合する(年収800万の求人で「月給800万円」は違反)。
- 再訪の1通目の羅列の判定: 正社員の短い職種名(営業・教育・物流)は、前後に漢字が続くとき(「営業時間」)は数えない。

相談から始まるペルソナ(`T-career-fulltime`、`T-side-job`、`T-student-first`、`T-blank-parent`)の期待どおりの出口
(`outcome_as_expected`)は、結果の記録ではなく、`expect_offer_by`(8)のターンまでに求人を見るかを聞いた(または探した)かで見る
(2026-10-04 のユーザーの決定、jyoka/tasks#133)。相談の決まり(5、6問で求人を見るかを聞く)に従うと、ターン上限 8 では
結果の記録に届かないことがあるため。ターン上限は基準と比べるため 8 のまま。判定は `evals/checks.py` の `jobs_offer_turn`:
求人を探した(`recommend_jobs`・`relax_conditions`・求人カード)か、疑問詞の無い「この内容で求人を見ますか?」の形の問い
(`OFFER_JOBS`。動詞と「ますか」の間は活用と補助の言い方だけで、「求人を探すのに不安はありますか?」は数えない)の最初のターン。H の保存済みの会話(`sim-20261004-113109`)で判定し直すと、`T-career-fulltime`(T7)、
`T-side-job`(T6)、`T-student-first`(T7)が合格、`T-blank-parent` が不合格になる(`tests/test_consult_offer.py`)。
相談から始まらない `T-switch-to-fulltime` と、`C-consult-*` は、これまでどおり記録した結果(`expect_outcome`)で見る。

## 12. 挨拶から 3 つの入口へ案内する(2026-10-25、会話の改善 (2/3))

音声相談、履歴書の読み込み、レジュメ・アーケード(ゲーム)は、経験を聞く 1 問や playbook の場面でしか出ず、本人が気づく場面が
ほとんど無かった。利用者の判断(「最初の挨拶の後に、こういった選択肢に誘導・案内しないといけない」)に沿って、挨拶から案内する。
Web のトーク画面でも LINE のトークでも同じ決まりで、どちらも dip の Prompt(`entries.json` の `visit`・`revisit` と、
`baitoru_assistant.md` の「挨拶で3つの入口を案内する」)だけで動く。LINE 側のランタイムには挨拶の業務知識を足していない。

### 初回訪問の挨拶

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 吹き出し | 1 つ目で何ができるか(相談と求人の提案、窓口で使える入口)を 1 文。2 つ目で「どれから始めますか?」の 1 問 | 1 回の返信で質問は 1 つ。入口があることを文でも伝え、ボタンだけが並んで意味が分からない状態にしない |
| 3 つの入口 | 窓口で使えるものを全部。`actions` に `voice_consult`、`resume_upload` の順、ゲームは `buttons` の「ゲームで書類を作る」(`arcade_url`) | 押しても発言にならない操作なので、`quick_replies`(押すと発言になる)とは別の形にする。どれも押せばその画面に進む |
| 文字の選択肢 | `quick_replies` は「求人を探す / まず相談する / 今はいい」の 3 つ、この順 | 文字で答えたい人と、今は何もしない人の逃げ道を残す。入口と合わせて押せるものが 6 つになるので、初めての人にはまだ使えない「応募履歴を確認」(アカウント連携の前で、aica に応募の記録が無い)を外した。「応募履歴を確認」は再訪のメニューと締めくくりの選択肢に残す |
| 並ぶ順 | Web は ゲームのボタン → 音声・履歴書のボタン → 文字の選択肢。LINE は 1 つのボタンのメッセージに ゲーム・音声・履歴書、文字の選択肢はクイックリプライ | 画面を開くボタン(`buttons`)を操作(`actions`)より先に描くのは、両方の窓口の今の描き方(`talk-core.js` の `renderReply`、`line_channel.to_messages`)で、どちらの窓口でも同じ順になる。描き方は変えていない |
| 要約 | 初回訪問でも最初に `get_user_conversation_summary` を読む | ゲームの URL(`arcade_url`)は要約にしか無いため |

### 再訪の挨拶

summary に合わせて 1 つだけ勧める。毎回 3 つ全部は並べない。上から順に見て、最初に当てはまり、窓口で使えるものを選ぶ(使えなければ次を見る)。

| 順 | 当てはまるとき | 勧め方 | 理由 |
|---|---|---|---|
| 1 | `arcade_draft` の `blank_lines` がある | 「数字の空欄が残っています」と 1 文、`quick_replies` に「空欄を埋める」 | 途中の書類の続きがいちばん近い次の一歩。下書きの保存の知らせ(`arcade_reply`)の選択肢と同じ文言にした |
| 2 | 経歴が分からない(`uploaded_resume` も、`stated_preferences` の `experience` も、`consultation_summary` も無い) | `actions` に `resume_upload` だけ | 経歴を話してもらう手間を省ける。利用者の例「履歴書が無ければ読み込み」 |
| 3 | 経歴は分かるが、`consultation_summary` が無い | `actions` に `voice_consult` だけ | 経歴の次に足りないのは、本人の目的や事情。話すと約 5 分で書類の下書きもできる |
| 4 | `arcade_draft` が無く、`arcade_url` がある | `buttons` に「ゲームで書類を作る」だけ | 経歴も相談もあれば、残るのは書類づくり |

- 勧める 1 文は確認の 1 問とは別にし、疑問符を付けない(1 回の返信で質問は 1 つ)
- 応募済みで連絡待ちの人(`applied_waiting`)と、応募フォームの途中離脱がある人(`form_exit`)には勧めない。応募のことを先にする
- 挨拶の入口の案内は、経験を聞く 1 問の「1 つの会話で 1 回だけ」に数えない。挨拶はメニューで、経験の 1 問は手間を省く場面だから

### 窓口で使えるものだけ

Web のトーク画面は、履歴書とゲームはいつも、音声相談は LiveKit の設定があるときだけ使える(`line_channel.web_features`。
設定が無いと音声相談の開始が 503 になるので、本番のトーク画面のターンでは「窓口」に音声相談を勧めないと書く。評価と開発者画面は 3 つとも使える扱い)。
LINE は LIFF の設定があれば履歴書とゲーム、音声相談は LiveKit の設定もあるときだけ(`line_channel.liff_features`)。エージェントはシステムプロンプトの「窓口」でそれを知り、使えないものはボタンも文も出さない。
LIFF の設定が無い LINE では、初回訪問は文字の選択肢だけ、再訪は何も勧めない(下書きの続きは文字の選択肢なので勧めてよい)。

### LINE のリッチメニュー

LINE では、トークの下に常に出しておけるリッチメニューも使う。音声相談、履歴書の読み込み、ゲーム、求人を探すの 4 つで、
前の 3 つは LIFF URL(`line_channel.liff_page_url`。トークのボタンと同じ画面)を直に開き、「求人を探す」はその文を本人の発言として送る
(新しいイベントは作らない)。音声相談は LiveKit の設定があるときだけ置く。LIFF の設定が無いときは作らない。
LINE に登録するのは人で、`scripts/line_rich_menu.py`(画像も作る)と README の「LINE のリッチメニュー」の手順を使う。
エージェントの返信はリッチメニューに頼らず、触れない(トークの選択肢で完結させる)。

### 評価

`evals/checks.py` の `greeting_entry_violations` が見る。窓口は `evals.run` の `--channel` と `--features` で決める(既定は Web)。

  期待の入口がその窓口で使えなければ、何を勧めたかは問わない(使えないものを出したら違反)

## 13. 最初の求人はエリアが分かってから出す(2026-10-25、会話の改善 C (3/10)、jyoka/tasks#224)

「3回目の返信までに分岐」と、playbook の「残りを聞いてから、にしない」が、最低限要る条件を決めていなかったため(#221 の推測)。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 最低限の条件 | エリア。要約(`stated_preferences` の area・`consultation_summary`)にも会話にも無ければ、探す前に 1 問で聞く。選択肢には、要約や行動から分かる駅・エリア(`tendency`・`last_application` の area)の候補があれば入れる | 通えない場所の求人は、ほかの条件が合っても役に立たない。エリアが分かれば、残りの条件は求人を見ながら絞れる |
| 「求人を探す」を選んだだけ | エリアと仕事の希望をまとめて 1 問で聞く(「どのエリアで、どんなお仕事を探しますか?」) | 実 API の 1 回目で、エリアだけを聞いて探すと、法人営業(正社員)や深夜バルなど、カフェを探す人に合わない求人が並んだ(ジャッジの design_fit 3.0)。まとめて聞けば、1 問で両方そろう |
| 「求人を見せて」 | エリアが無ければ、エリアだけを 1 問で聞いてから探す。仕事の希望を含め、ほかの条件は聞き足さず、分かっていること(経験など)で探す | 本人は待ちきれずに頼んでいる。聞くのはどうしても要る 1 つだけにする。実 API の 2 回目で、エリアと仕事をまとめて聞いたので、場面を分けて書いた |
| エリアなしで探してよいとき | 本人がエリアを問わない(「どこでもいい」「エリアは特にない」)か、在宅の仕事(`remote=可`)を探すとき | 本人が決めたこと。在宅はエリアが要らない |
| keywords | 分かっている経験(`stated_preferences` の experience、この会話で話した経験。未経験なら「未経験」)と希望の仕事を、本人の言葉で入れる | `keywords` は意味の近さで並べるので、経験に近い求人が上に来る。職種の一覧にある希望は `job_type` にも渡す |
| 分岐の期限 | エリアを聞く 1 問は、3 回目の返信までの回数に数えない(1 回だけ) | 期限に収めるために、エリアを聞かずに探すことを防ぐ |

評価(`evals/checks.py`)で見ること。どれもオフラインのテストが `tests/test_checks.py` にある。

- `area_violations`(違反に数える): `recommend_jobs` を `area` なしで呼んだ。エリアが分かっていなかったか、分かっていたのに入れなかったかを分けて書く。
  本人がエリアを問わないと言った、`remote=可` で探した、前のターンでエリアつきで探した後に広げた、は除く。
  「問わない」は、答えに地名が無いときだけ数える(「渋谷で。仕事内容は特にこだわりません」の「こだわりません」は仕事のこと)。
  後で地名を言い直したら、問わない言い方は打ち消す。「広げた」は、`relax_conditions` を見せたか、本人が「広げて」「外して」と言ったときだけで、
  本人が前の検索に無い地名を言ったら(「やっぱり池袋で」)言い直しとして違反にする。どれも、分かっているエリアを落とした検索を見逃さないため。
  「在宅」「リモート」は、在宅で働きたいという言い方だけを「問わない」に数える。「リモートは無理なので」「在宅は苦手」のように在宅を外す言い方は数えず、
  同じ発言に地名があれば地名を優先する(エリアは分かっていないか、分かっている)。
  判定の正規表現は目安とする(利用者の決定、2026-10-26)。言い方は無数にあり、塞ぐたびに別の穴が出るため。直すのは、Goal の例と
