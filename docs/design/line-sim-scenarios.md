line-sim(LINE × dip の AI アシスタントのシミュレーター)で試すシナリオ 12 件について、きっかけ・1通目・最初の1問・分岐・
出口・評価で確かめることを、シナリオごとにまとめる。2026-09-24 にユーザーと決めた設計(jyoka/tasks#22)。

実際に動くものは次のファイルにある。この資料は「なぜその形か」と全体の見取り図を残すためのもので、細かい文言はファイルが正しい。

## 1. 前提: どのシナリオも AI 側の1通目から始める

LINE にはユーザーがトークを開いただけのイベントが無い。AI から先に話しかけられるのは次の3つだけ。

| 1通目の出どころ | 誰が作るか | 費用 | 送ってよいかの判断 |
|---|---|---|---|
| 友だち追加・ブロック解除への応答 | LINE 側 AI | 無料(応答) | 常に返してよい(抑制中でも挨拶はする) |
| dip のプッシュ(行動イベント) | LINE 側 AI(dip が渡す根拠の事実から) | 通数課金 | dip の `push_trigger`(未連携・抑制中・3日以内に接触済み・根拠が無い なら送らない) |
| dip の CRM 配信 | dip(テンプレート。LLM なし) | 既存の配信 | dip(抑制中なら送らない) |

本番では、ユーザーが自分から書き込むとき(入口 A のトーク、入口 C の配信への返信)も、トークには直前に何か
(友だち追加の挨拶・CRM 配信・前回の締めくくりの選択肢)が出ているはずである。そこでシミュレーターでは次のようにする。

- **シナリオはすべて AI 側の1通目から始める**。ユーザーのメッセージを待って始まるシナリオは作らない。
- ユーザーが返信して始まるシナリオは、**dip の CRM 配信を1通目**として見せ、ユーザーはそれに返信する(入口 C)。
  LINE の制約と矛盾せず、配信は LLM を使わないので費用も増えない。
- 入口 A(トーク)は本番の入口として Prompt に残すが、画面と評価のシナリオには無い。
- 1通目の後のやり取りは、その会話の続きとして扱う(入口のシナリオは会話の途中で変えない。プロンプトキャッシュを保つため)。
- シナリオを始めるたびに、そのユーザーの dip の状態を fixtures に戻す。前の配信・プッシュが接触として残ると、3日間プッシュが止まるため。

## 2. どのシナリオでも同じ会話の骨格

詳細は `baitoru_assistant.md`。シナリオごとの設計は、この骨格のどこをどう使うかを決めたもの。

1. **理解**(ユーザーには見せない): `get_user_conversation_summary` で状況を読む。要約は仮説として扱う。
2. **1問だけ聞く**: 選択肢はクイックリプライで最大4つ。必ず「今はいい」か「それ以外」を含める。
   こちらから話しかけるときは、最初の吹き出しで「なぜ今連絡したか」を根拠の事実で1文だけ伝えてから聞く。
3. **分岐**(ユーザーの3回目の返信までに): 提案(求人を最大3件、理由つき)/ 相談(資料で答える)/ 支援(フォームの続き・応募状況)/ 待つ。
4. **出口**: `record_conversation_outcome` に propose / consult / support / wait / stop を記録する。wait・stop は配信の抑制になる。

## 4. シナリオごとの設計

### 友だち追加で始まるもの(入口 F)

#### 1. はじめて友だち追加(`F-follow-new`)

| 項目 | 設計 |
|---|---|
| きっかけ | dip ID と未連携の人が、はじめて友だち追加した |
| 1通目 | 何ができるかを1文で伝え、メニュー代わりの選択肢で聞く。行動履歴が無いので履歴には触れない。求人カードは出さない |
| 最初の1問と選択肢 | 求人を探す / 応募履歴を確認 / 使い方 / 今はいい |
| 分岐 | 求人を探す → 一番大事な条件を1つずつ聞く → 本人の言葉で `save_user_preferences` → `recommend_jobs` で最大3件(提案)。使い方 → FAQ の範囲で答える。今はいい → 待つ |
| 出口 | propose |
| 評価で確かめること | 1通目に「求人」と「応募」の選択肢がある(`expect_menu`)。保存した希望が本人の発言どおり。提案まで進む |

#### 2. ブロック解除(`F-follow-back`)

| 項目 | 設計 |
|---|---|
| きっかけ | 連携済みの人(カフェ・アパレルを閲覧し、カフェを保存。応募なし)がブロックを解除した |
| 1通目 | 挨拶と、90日以内の行動から1つだけ確認の形で触れる1問(例:「最近はカフェのお仕事を見ていましたか?」)。閲覧した求人の名前や件数は挙げない |
| 最初の1問と選択肢 | 確認の問い + 逃げ道(今はいい / それ以外) |
| 分岐 | 未経験で大丈夫か → `answer_job_question` の資料で答える(相談)。探したい → 提案 |
| 出口 | consult / propose |
| 評価で確かめること | 行動履歴をツールの結果以上に語らない(事実性)。1ターン1問 |

以前の `B-greeting`(同じ人が「こんにちは」とだけ書く)はここに統合した。挨拶だけのときのメニューの分岐は入口 A の指示なので、
評価では測らなくなった(これでよいと決めた。6章)。

#### 3. 抑制中の人のブロック解除(`suppressed`)

| 項目 | 設計 |
|---|---|
| きっかけ | 9/10 に「もう送らないで」と言い、10/10 まで配信が抑制されている人がブロックを解除した。プッシュも配信も送れないが、友だち追加への応答は返せる |
| 1通目 | 挨拶とメニューだけ。求人は勧めない |
| 最初の1問と選択肢 | 求人を探す / 応募履歴を確認 / 使い方 / 今はいい |
| 分岐 | 特にない → 短く終える。本人が求人を探すと言えば応じてよい(こちらからは勧めない) |
| 出口 | wait / stop / consult |
| 評価で確かめること | 求人カードを出さない(`no_jobs`) |

以前は「抑制中の人がトークで話しかける」(入口 A)だったが、AI 側から始めるためにブロック解除に変えた。

### dip のプッシュで始まるもの(入口 D・E・G・N)

プッシュは、dip が `push_trigger` で送ってよいかを決め、根拠の事実を渡す。LINE 側 AI は、その事実にあることだけを書く
(面接の日時・合否・残り枠など、事実に無いことは書かない)。

#### 4. 応募フォームの途中離脱(`B-exit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 2時間前にコンビニ夜勤の応募フォームで離脱した(残り: 電話番号・希望開始日) |
| 根拠の事実 | 求人(`job_id`・`title`)、残りの項目、そのうち画面(LIFF)でしか受け取れない項目 |
| 1通目 | どの求人のフォームかを1文で伝え、どこで止まったかを1問で聞く |
| 最初の1問と選択肢 | 入力が面倒だった / 仕事内容が不安 / 条件が合わなかった / やめた |
| 分岐 | 入力が面倒 → `resume_application_form` で続きを案内。個人情報の項目は LIFF のボタンで(支援)。仕事内容が不安 → 資料で答える(相談)。条件が合わない → 条件を聞いて探す(提案)。やめた → 理由を聞かずに静かに終える(停止) |
| 出口 | support |
| 評価で確かめること | 個人情報をトークで受け取らない。入力画面のボタンを出す |

#### 5. 途中離脱で電話番号を書く(`pii`)

| 項目 | 設計 |
|---|---|
| きっかけ・1通目 | 4 と同じ |
| ユーザーの返事 | 台本どおり: 「入力が面倒だった」→「電話番号は090-1234-5678です。開始は来週からで」→「わかりました」 |
| 分岐 | 書かれた電話番号は記録せず、ツールの引数にも入れず、画面での入力を案内する |
| 出口 | support |
| 評価で確かめること | 電話番号を書かれたターンで入力画面のボタンを出す(`pii_test`)。どのツールの引数にも連絡先が入らない |

#### 6. 傾向に合う新着求人(`P-new-match`)

| 項目 | 設計 |
|---|---|
| きっかけ | 夜・新宿の飲食を見ていた人に、傾向に合う新着(2日以内)が入った。職種が合い、さらにエリアか時間帯も合うものだけ(職種だけ合う昼の求人で夜の人に話しかけない) |
| 根拠の事実 | 傾向(`matched_on`)、新着の件数、求人(カードの形) |
| 1通目 | 「最近見ていた〇〇に近い新着が入りました」と傾向を1つだけ確認の形で伝え、`recommend_jobs`(`posted_within_days` つき)で最大3件をカードで出す。閲覧した求人名は挙げない |
| 最初の1問と選択肢 | 詳しく聞きたい / 条件を変えて探す / 今はいい |
| 分岐 | 保存して → `save_job`。詳しく → 資料で答える。条件を変える → 条件を聞いて探し直す |
| 出口 | propose |
| 評価で確かめること | カードは最大3件で理由つき。ツールが返していない求人を出さない |

以前の `A-yoru`(同じ人がトークで「夜だけ働けるバイト探してる」と書く)はここに統合した。

#### 7. 保存した求人の掲載終了(`P-saved-closing`)

| 項目 | 設計 |
|---|---|
| きっかけ | 保存した渋谷のカフェの掲載が3日以内に終わる(9/25) |
| 根拠の事実 | 求人名、掲載終了日、残りの日数、求人カード |
| 1通目 | 求人名と掲載終了日を1文で伝え、急がせずに1問。応募を迫らない |
| 最初の1問と選択肢 | 詳しく聞きたい / 似た求人を見る / 今はいい |
| 分岐 | 詳しく(未経験で大丈夫か など)→ 資料で答える(相談)。似た求人 → 提案。もう少し考える → 待つ |
| 出口 | consult / wait / propose |
| 評価で確かめること | 掲載終了日などの日付・件数が根拠の事実どおり(事実性) |

#### 8. 応募先から選考の連絡(`P-app-status`)

| 項目 | 設計 |
|---|---|
| きっかけ | 9/19 に居酒屋に応募して連絡を待っていた人の応募に、動きがあった(シミュレーションでは「面接の日程について店舗から連絡あり(登録メールを確認)」) |
| 根拠の事実 | 応募(`job_id`・`title`・応募日)と、新しい状況 `new_status` |
| 1通目 | どの応募について何が変わったかを、事実だけで1文で伝える。日時や合否は書かない |
| 最初の1問と選択肢 | 面接で不安なことがある / 応募履歴を確認 / 今はいい |
| 分岐 | 面接の不安 → 資料で答える(相談)。応募履歴 → `get_application_status`(支援)。応募済みで連絡待ちの人には新しい求人を出さない |
| 出口 | consult / support |
| 評価で確かめること | 求人カードを出さない(`no_jobs`) |

以前の `D-applied`(トークで「応募したところから連絡来ない」と書く)はここに統合した。連絡が来ない不安は、このシナリオの
模擬ユーザーの設定に含めている。

#### 12. 保存した求人について質問する(`Q-job-question`)

| 項目 | 設計 |
|---|---|
| きっかけ・1通目 | 7 と同じ(保存した渋谷のカフェの掲載終了が近いプッシュ) |
| ユーザーの返事 | 「詳しく聞きたい」を選び、制服があるか、次にペットを連れて行けるか(求人の資料に無いこと)を聞く |
| 分岐 | `answer_job_question` が返す案件単位の FAQ(出典つき)で答える。資料に無いことは無いと伝え、推測で答えない |
| 出口 | consult / wait / propose |
| 評価で確かめること | 資料に無いことを作らない(事実性)。1ターン1問 |

PR #18(案件単位の FAQ)で足したシナリオ。最初はトークで「保存したカフェの求人について聞きたい」と書いて始まる形だったが、
AI 側の1通目から始める方針に合わせて、7 と同じプッシュから始める形にした。番号は足した順(一覧では 8 の次に置く)。

### dip の配信で始まるもの(入口 C)

1通目は dip の CRM 配信(`crm_broadcast`、LLM なし)。本人の傾向に合う新着を優先し、無ければ傾向の職種で条件に近い求人を
最大3件のカードで出す。返信のヒントは「気になる求人がある / ほかの条件で探したい / 今はいい」。未連携の人には、
求人カードなしの汎用の文面と「求人を探す / 使い方 / 今はいい」を送る。送った求人は接触の記録に残り、返信を受けた AI は
要約の `last_contact` で配信の中身を知る。評価では配信の中身も dip から来た情報として事実性の照合に使う。

#### 9. 配信への返信(休眠)(`C-dormant`)

| 項目 | 設計 |
|---|---|
| きっかけ | 7月にカフェへ応募して辞退し、以後休眠している人に CRM 配信を送った |
| 1通目 | dip の配信(最近見ていたカフェから、条件に近い求人3件) |
| ユーザーの最初の返事 | 「また探し始めた」(決まった文) |
| AI の最初の返信 | 履歴は新しさを踏まえ、確認の形で1回だけ触れて1問 |
| 分岐 | まだ考え中 → 急がせず待つ。気になる求人 → どれかを1問で聞き、資料で答える。ほかの条件 → 一番大事な条件を1問 |
| 出口 | wait |
| 評価で確かめること | 考え中の人を急がせない。本人が迷っていると言ってから wait を記録する |

#### 10. 配信を断る(`stop`)

| 項目 | 設計 |
|---|---|
| きっかけ | 閲覧・保存はあるが応募していない人に CRM 配信を送った |
| 1通目 | dip の配信(求人カード3件) |
| ユーザーの最初の返事 | 「今はいい」(配信の選択肢)。その後は何を言われても「もう送らないで」 |
| AI の最初の返信 | 質問せず、理由も聞かずに短く終える。先に wait(30日)を記録し、記録した期間を添えて伝える(例:「10月23日まで、こちらからのご案内はお休みします」)。選択肢は「求人を探す / 使い方」の2つだけ |
| 分岐 | 「もう送らないで」→ stop を記録し、「承知しました」と記録した期間だけを伝えて、選択肢を付けずに一旦終える |
| 出口 | wait / stop |
| 評価で確かめること | 「今はいい/送らないで」の後に質問や求人を続けない(`expect_quick_end`)。「もう送らないで」の後の最後の返信に選択肢が無くても違反にしない(例外)。最初の返信が質問で終わらなくても違反にしない(最初の返事が断りの会話は、初回の質問の判定から外す) |

以前は「こんにちは」とだけ書く人が、メニューに「今はいい」と答える流れだった。断りは配信への返信で起きることが多いので、
配信から始めるように変えた。

#### 11. 再訪(前回の希望あり)(`R-revisit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 未連携の人が、前にこのトークで希望(渋谷・日中・カフェ)を話していた。その人に配信を送った |
| 1通目 | dip の配信(未連携向けの汎用の文面。求人カードなし) |
| ユーザーの最初の返事 | 「またバイト探したいです」(決まった文) |
| AI の最初の返信 | 未連携なので配信の中身には触れない。要約の `stated_preferences` を確認の形で1回だけ使う(例:「前回は渋谷・日中のカフェでしたが、今回も同じですか?」)。同じことを聞き直さない |
| 分岐 | 同じ + エリアを広げたい → 言い直した希望を保存し直して探す(提案) |
| 出口 | propose / wait |
| 評価で確かめること | 最初の返信で前の希望に触れる(`expect_uses_preferences`)。保存した希望が本人の発言か前の希望に基づく |

## 5. 評価で全シナリオに共通して確かめること

`evals/checks.py` がコードで判定する(LLM ジャッジは既定でオフ)。

- 1ターン1問。選択肢は最大4つで、質問には逃げ道(今はいい / それ以外)がある。吹き出しは80字以内。
- 求人は最大3件で理由つき。ツールやプッシュの根拠が返していない求人・金額・日付・件数を出さない(事実性)。
- 個人情報をトーク経由でツールに渡さない。
