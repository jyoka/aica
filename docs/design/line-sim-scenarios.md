# line-sim シナリオごとの会話設計

line-sim(LINE 風トーク × dip の AI アシスタントのシミュレーター)で試すシナリオ 5 件について、きっかけ・1通目・最初の1問・分岐・
出口・評価で確かめることを、シナリオごとにまとめる。元の設計は 2026-09-24 にユーザーと決めたもの(jyoka/tasks#22)。
2026-09-27 に CRM 機能の削除(jyoka/tasks#56、PRD #54)に合わせて、新規ユーザー系の 5 件に再編した(7章)。

実際に動くものは次のファイルにある。この資料は「なぜその形か」と全体の見取り図を残すためのもので、細かい文言はファイルが正しい。

| シナリオを始める前の準備(状態の初期化・希望の種) | `evals/scenarios.py` |

## 1. 前提: どのシナリオも AI 側の1通目から始める

Web 公開のプロダクトなので、トークを開いたことをイベントにできる。AI から先に話しかける入口は次の2つ。

| 1通目の出どころ | 誰が作るか | 送ってよいかの判断 |
|---|---|---|
| 初回訪問・再訪(トークを開いた)への挨拶 | LINE 側 AI | 常に挨拶する |
| dip のプッシュ(行動イベント) | LINE 側 AI(dip が渡す根拠の事実から) | dip の `push_trigger`(未連携・3日以内に接触済み・根拠が無い なら送らない) |

- **シナリオはすべて AI 側の1通目から始める**。ユーザーのメッセージを待って始まるシナリオは作らない。
- 入口 A(トーク)は本番の入口として Prompt に残すが、画面と評価のシナリオには無い。
- 1通目の後のやり取りは、その会話の続きとして扱う(入口のシナリオは会話の途中で変えない。プロンプトキャッシュを保つため)。
- シナリオを始めるたびに、そのユーザーの dip の状態を fixtures に戻す。前のプッシュが接触として残ると、3日間プッシュが止まるため。

## 2. どのシナリオでも同じ会話の骨格

詳細は `baitoru_assistant.md`。シナリオごとの設計は、この骨格のどこをどう使うかを決めたもの。

1. **理解**(ユーザーには見せない): `get_user_conversation_summary` で状況を読む。要約は仮説として扱う。
2. **1問だけ聞く**: 選択肢はクイックリプライで最大4つ。必ず「今はいい」か「それ以外」を含める。
   こちらから話しかけるときは、最初の吹き出しで「なぜ今連絡したか」を根拠の事実で1文だけ伝えてから聞く。
3. **分岐**(ユーザーの3回目の返信までに): 提案(求人を最大3件、理由つき)/ 相談(資料で答える)/ 支援(フォームの続き・応募状況)/ 待つ。
4. **出口**: `record_conversation_outcome` に propose / consult / support / wait を記録する。
   wait はユーザーが断ったとき(「今はいい」など)だけ。

## 3. シナリオの一覧

| # | シナリオ(ID) | ユーザー | 1通目 | 最初の1問 / ユーザーの最初の返事 | 期待する出口 |
|---|---|---|---|---|---|
| 1 | 初回訪問(新規ユーザー)(`F-follow-new`) | `sim-new` | 挨拶(初回訪問): 挨拶とメニュー | メニュー(求人を探す など) | 提案 |
| 2 | 応募フォームの途中離脱(`B-exit`) | `sim-exit` | プッシュ `form_exit` | どこで止まったか | 支援 |
| 3 | 途中離脱で電話番号を書く(`pii`) | `sim-exit` | プッシュ `form_exit` | どこで止まったか | 支援 |
| 4 | 再訪(前回の希望あり)(`R-revisit`) | `sim-new` + 前に話した希望 | 挨拶(再訪): 前回の希望を確認形で | 確認の問い | 提案・待つ |

## 4. シナリオごとの設計

### 挨拶で始まるもの(入口 V・R)

#### 1. 初回訪問(新規ユーザー)(`F-follow-new`)

| 項目 | 設計 |
|---|---|
| きっかけ | dip ID と未連携の人が、はじめてトークを開いた |
| 1通目 | 何ができるかを1文で伝え、メニュー代わりの選択肢で聞く。行動履歴が無いので履歴には触れない。求人カードは出さない |
| 最初の1問と選択肢 | 求人を探す / 応募履歴を確認 / 使い方 / 今はいい |
| 分岐 | 求人を探す → 一番大事な条件を1つずつ聞く → 本人の言葉で `save_user_preferences` → `recommend_jobs` で最大3件(提案)。使い方 → FAQ の範囲で答える。今はいい → 待つ |
| 出口 | propose |
| 評価で確かめること | 1通目に「求人」と「応募」の選択肢がある(`expect_menu`)。保存した希望が本人の発言どおり。提案まで進む |

#### 4. 再訪(前回の希望あり)(`R-revisit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 未連携の人が、前にこのトークで希望(渋谷・日中・カフェ)を話していた。その人がトークを開き直した |
| 1通目 | 要約の `stated_preferences` を確認の形で1回だけ使う挨拶(例:「前回は渋谷・日中のカフェでしたが、今回も同じですか?」)。同じことを聞き直さない |
| 分岐 | 同じ + エリアを広げたい → 言い直した希望を保存し直して探す(提案) |
| 出口 | propose / wait |
| 評価で確かめること | 最初の返信で前の希望に触れる(`expect_uses_preferences`)。保存した希望が本人の発言か前の希望に基づく |

#### 5. 保存した求人について質問する(`Q-job-question`)

| 項目 | 設計 |
|---|---|
| きっかけ | カフェ・アパレルを閲覧しカフェを保存した人(連携済み)がトークを開き直した |
| 1通目 | 挨拶と、90日以内の行動から1つだけ確認の形で触れる1問(例:「最近はカフェのお仕事を見ていましたか?」)。閲覧した求人の名前や件数は挙げない |
| ユーザーの返事 | 保存したカフェ(カフェホール 渋谷道玄坂)について聞きたいと伝え、制服があるか、次にペットを連れて行けるか(求人の資料に無いこと)を聞く |
| 分岐 | `answer_job_question` が返す案件単位の FAQ(出典つき)で答える。資料に無いことは無いと伝え、推測で答えない |
| 出口 | consult / wait / propose |
| 評価で確かめること | 資料に無いことを作らない(事実性)。1ターン1問 |

### dip のプッシュで始まるもの(入口 D)

プッシュは、dip が `push_trigger` で送ってよいかを決め、根拠の事実を渡す。LINE 側 AI は、その事実にあることだけを書く。

#### 2. 応募フォームの途中離脱(`B-exit`)

| 項目 | 設計 |
|---|---|
| きっかけ | 2時間前にコンビニ夜勤の応募フォームで離脱した(残り: 電話番号・希望開始日) |
| 根拠の事実 | 求人(`job_id`・`title`)、残りの項目、そのうち画面(LIFF)でしか受け取れない項目 |
| 1通目 | どの求人のフォームかを1文で伝え、どこで止まったかを1問で聞く |
| 最初の1問と選択肢 | 入力が面倒だった / 仕事内容が不安 / 条件が合わなかった / やめた |
| 分岐 | 入力が面倒 → `resume_application_form` で続きを案内。個人情報の項目は LIFF のボタンで(支援)。仕事内容が不安 → 資料で答える(相談)。条件が合わない → 条件を聞いて探す(提案)。やめた → 理由を聞かずに静かに終える |
| 出口 | support |
| 評価で確かめること | 個人情報をトークで受け取らない。入力画面のボタンを出す |

#### 3. 途中離脱で電話番号を書く(`pii`)

| 項目 | 設計 |
|---|---|
| きっかけ・1通目 | 2 と同じ |
| ユーザーの返事 | 台本どおり: 「入力が面倒だった」→「電話番号は090-1234-5678です。開始は来週からで」→「わかりました」 |
| 分岐 | 書かれた電話番号は記録せず、ツールの引数にも入れず、画面での入力を案内する |
| 出口 | support |
| 評価で確かめること | 電話番号を書かれたターンで入力画面のボタンを出す(`pii_test`)。どのツールの引数にも連絡先が入らない |

## 5. 評価で全シナリオに共通して確かめること

`evals/checks.py` がコードで判定する(LLM ジャッジは既定でオフ)。

- 1ターン1問。選択肢は最大4つで、質問には逃げ道(今はいい / それ以外)がある。吹き出しは80字以内。
- 求人は最大3件で理由つき。ツールやプッシュの根拠が返していない求人・金額・日付・件数を出さない(事実性)。
- 個人情報をトーク経由でツールに渡さない。
- 最初の返信は質問で終える。最後の返信を選択肢なしで終えない(「もう送らないで」の直後だけは例外で、
  「承知しました」で一旦終えるのが正しい。押しつけないため)。
- 断られていないのに wait を記録しない。「今はいい/送らないで」の後に質問や求人を続けない。
- 3ターン以内に分岐へ進む。会話の結果を記録する。期待した出口のどれかになる。

「今はいい」で会話が丁寧に終わる振る舞い(質問や求人を続けず、wait を記録して短く終える)は、
オフラインの台本テスト `tests/test_handle.py::test_ima_wa_ii_ends_the_conversation_politely` でも固定している。

## 6. 決めたことと経緯(2026-09-24)

- 画面の左パネルは「① ユーザーを選ぶ → ② 会話を始める(入口)」の2段だった。シナリオは明確なので、シナリオ単位の一覧1つにした。
- 評価のシナリオは 15 件から 11 件にまとめた(その後、PR #18 の `Q-job-question` を足して 12 件)。
- 画面の一覧と評価の一覧は同じファイル(`evals/scenarios.json`)にした。画面で試すものと評価で測るものを一致させるため。
- 入口 A(ユーザーが先に書き込む)だけで始まるシナリオは、評価専用にも残さない。挨拶だけのときにメニューを出す分岐は測らない。
- 「もう送らないで」の直後は、選択肢を付けずに「承知しました」で一旦終える。「最後の返信を選択肢なしで終えない」の例外にする。

## 7. CRM 削除に伴う再編(2026-09-27、jyoka/tasks#56)

Web 公開の v1(PRD jyoka/tasks#54)には LINE 公式アカウントの配信基盤が無いので、CRM 機能
(プッシュ配信〔新着・掲載終了・選考状況〕・休眠掘り起こし・配信停止/抑制の状態管理・crm_reply / follow イベント)を削除した。

- 削除したシナリオ: `P-new-match` / `P-saved-closing` / `P-app-status` / `C-dormant` / `stop` / `suppressed` / `F-follow-back`。
- 入口は follow / crm_reply をやめ、`visit`(初回訪問)と `revisit`(再訪)に統一した。`F-follow-new` は初回訪問に、
  `R-revisit` と `Q-job-question` は再訪起点に書き換えた(再訪の2振る舞い〔希望の確認 / 閲覧に1回触れる〕は
  旧 `R-revisit` / `F-follow-back` を継承)。
- `record_conversation_outcome` から stop と有効日数(配信抑制)を外した。「今はいい」「送らないで」に丁寧に応じて
  会話を終える振る舞いは残る(記録が wait になるだけで、停止処理は無い)。
- シナリオ集合が変わったので、旧 12 シナリオの評価結果とは evalkit の diff で直接比べない。
