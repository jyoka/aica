# 設計: 個人情報の扱い(公開の前)

aica を外に公開する前に、個人情報をどこへ送り、どこに、どれだけの期間置くかを決めます。
利用規約とプライバシーポリシーの下書き([docs/legal/](../legal/))は、この設計の推奨案を前提にしています。
このメモではコードを変えません。実装は最後の「実装の task の分け方」の task で行います。

- 対象は今の main(`416a477`)です。行番号はこの版のものです
- 語は [HLD](../architecture/hld.md) の 10 章「用語」に従います
- [review-2026-10.md](../architecture/review-2026-10.md) の R7「個人情報を保存する範囲と期間が決まっていない」に答える文書です
- 外部サービスの保持の決まりは、2026-10-25 に各社の公開文書で確かめました(7 章)。契約や設定で変わるので、公開の前にもう一度確かめます
- 法律の扱いは、公開前に人が確認する前提の下書きです。法律の助言ではありません
- 例に出す値はすべて架空です

## 結論

| 決めること | 推奨 | 理由 |
|---|---|---|
| 履歴書を送る前に消すもの | ファイル名を送らない。写真と個人欄は、送る前に本人に隠してもらう案内と同意で扱う。次の段階で、PDF にテキストがあるときは画像を外してテキストだけを送る(3.2) | 氏名と住所はコードでは確実に見分けられない。画像の上で消すのは書式に左右される |
| トークの本文 | 電話、メール、住所らしい所を、会話に入れる前に伏せる(3.2) | aica はこれらを使わない。LLM にも会話の保存にも要らない |
| system prompt の LINE のユーザーID | 外す(3.2) | `PinUserMiddleware` がツールの `line_user_id` を固定しているので、LLM が知る必要がない |
| 外部サービスの保持 | OpenAI の `store` を切る。Deepgram の改善プログラムから外れる。LiveKit の録音を切る(プランは無料の Build のまま。利用者の決定)。Cartesia は確かめずに使う(利用者の決定)。本番の STT は Deepgram に固定する(3.2) | 設定とプランで、各社に残る量と学習への利用が減る |
| 保存する期間 | 会話は最後のやりとりから 30 日。使われなくなったユーザーは最後の利用から 180 日。費用台帳の ID は 90 日(3.3) | 30 分で会話は切れ、次の会話は要約から始まる。古い会話は、前の問いのボタンの答えを続けるときのほかは機能に使っていない |
| 音声相談のファイル | 本番では `data/voice-resume/` に書き出さない(3.3) | 同じ下書きは dip の状態にある。文字起こしは下書きを作った後は使わない |
| 消し方 | 毎日 1 回の掃除で期間を過ぎたものを消し、SQLite は VACUUM する(3.3) | 消した行がファイルの空き領域に残らないように |
| ログ | ID、種類、件数、有無、例外の型名だけ。値は出さない(3.4) | ログはホスティングの保持の決まりで残り、本人が消せない |
| AI Gateway | 本文のログを残さない。キャッシュも使わない(3.5)。**利用者が決めたこと** | ゲートウェイに本文が残ると、個人情報が Cloudflare にも残る |
| 同意 | Web は最初にトークを開いたとき、LINE は最初の発言の前か、LIFF の画面を最初に開いたときに、明示のボタンで取る。履歴書と音声は使う直前にもう一度示す(3.6) | 海外の事業者(Anthropic、OpenAI など)に送るので、何をどの国へ送るかを先に示して同意を取る |
| 本人が見る、消す | Web はプロフィール画面に「書き出す」を足す。LINE は「データを見る」「データを消す」のコマンドを足す(3.7) | 今の LINE のユーザーは、プロフィール画面を開けず、見ることも消すこともできない |

### 人が決めること

このメモでは決められず、公開の前に人が決めることです。下書きの【】の所に入ります。

- 運営者の名前(個人か法人か)、住所、代表者、問い合わせの窓口
- 公開する aica で出す求人が架空のデモか。架空なら、規約と画面にそう書く
  - 応募フォームの続きの画面(2.1 の #25)は、「氏名」「電話番号」などの必須の入力欄を出します。ポリシーの「名前、住所、電話番号、メールアドレスは、お尋ねしません」と食い違います。
    推奨: デモのままなら、公開の前に入力欄を外し、確定のボタンだけにする(値を受け取らなければ、尋ねたことにならないため)。本物の応募にするなら、ポリシーのその文と第三者提供の項を直す
- 連携先の求人サービス(今の dip はシミュレーション)を本物にするか。本物にするなら、アカウント連携は第三者提供になり、連携のときに同意が要る
- 保存期間の数(30 日、180 日、90 日)。理由は 3.3 にあるが、使われ方を見て変えてよい
- OpenAI の Zero Data Retention を申し込むか(審査と追加の条件がある。7 章)
- LiveKit Cloud を有料プランにするか。無料プランのままなら、ポリシーに改善への利用を書く(3.2「音声」)
- Cartesia の学習と保持の扱いを確かめた結果、そのまま使うか(3.2「音声」)
- 法律の確認を誰に頼むか(弁護士など)

## 1. 前提

- 公開の形は Render の Web サービスと音声ワーカーの 2 つのサービスです(HLD の 7 章)。`data/` は Web サービスのコンテナのディスクに
  だけ置きます。音声ワーカーは、相談の結果と dip の読み書きを Render の private network で Web サービスに送り、ディスクを持ちません
- 使う人は一般の求職者です。アルバイトを探す高校生など、18 歳未満も使うと考えます
- aica のログインはありません。Web は Cookie の匿名ユーザーID(`w-…`)、LINE は鍵つきのハッシュの LINE のユーザーID(`l-…`)で人を分けます
- 匿名ユーザーIDそのものは名前ではありません。ただ、その ID にひも付く会話や履歴書の読み取り結果には、本人が分かる内容が入りえます。
  なので、この設計では、ユーザーにひも付くデータはすべて個人情報として扱います
- 履歴書とトークには、病歴、障害、犯罪歴などの要配慮個人情報が入りえます(例: 「持病があるので夜勤は避けたい」)。
  aica からは聞きませんが、本人が書くことは止められません
- dip の行動の元データ(`data/dip_events.db`)と会員のログインは、今はシミュレーションの架空のデータです。
  ただし、公開した aica の本番のユーザーが書いた分(保存、応募など)は `data/state.json` の `dip_writes` に入ります

## 3. 設計

### 3.1 原則

1. 機能に要らないものは、送らない、残さない
2. 残すものには期限を付け、期限が来たら機械で消す
3. 外部サービスは、学習に使わせず、先方の保持が短くなる設定にする
4. ログには値を出さない
5. 本人が、自分のデータを見る、消す手段を、どのチャネルでも持つ
6. 送る先と国を、送る前に本人に示して同意を取る

個人情報保護法は、利用目的に要らなくなった個人データを遅滞なく消すよう努めることを求めています(22 条)。2 の期限はこれに沿います。

### 3.2 送る前に消すもの

#### 履歴書のファイル(#1、#2)

氏名、住所、写真を LLM の事業者(今は既定で Anthropic、前は OpenAI)に送らずに済むかの案です。

| 案 | 中身 | よい点 | 弱い点 |
|---|---|---|---|
| A. 今のまま | ファイルをそのまま送り、出力から電話、メール、郵便番号を消す | 読み取りの質が一番よい | 写真と氏名、住所が OpenAI に届く |
| B. テキストだけ送る | PDF にテキストがあれば、ローカルで取り出し、画像(写真)を外して送る。テキストの無い PDF と画像は A と同じ | 写真を送らない。仕組みが単純 | 氏名と住所はテキストに残る。スキャンや写真の履歴書には効かない |
| C. テキストを伏せて送る | B に加え、ローカルで電話、メール、郵便番号、住所らしい行、「氏名」欄の行を伏せる | 送る個人情報がさらに減る | 書式によって氏名の行を見分けられない。伏せすぎると職歴まで消える |
| D. 画像の上で消す | 履歴書の上の個人欄の位置を見つけて塗りつぶす | 画像でも写真を送らない | JIS の様式以外では位置が決まらない。外すと個人欄がそのまま届く |
| E. 本人に隠してもらう | アップロードの直前に「氏名、住所、写真の欄は隠すか消してから」と案内し、送る先と国を示して同意を取る | 確実で、コードが要らない | 本人が隠さなければ届く |

**推奨: E と、確実にできる小さな締め付けを最初に入れる。B は次の段階で入れる。C と D は入れない。**

- 最初に入れるもの
  - E の案内と同意(3.6)
  - ファイル名を送らない。`content_part` の `filename` を、形式だけの固定の名前(例 `resume.pdf`)にする(`resume_intake/extract.py:69`)
  - `responses.parse` に `store=False` を付ける(OpenAI に応答を残さない)
- 理由
  - 氏名はコードでは確実に見分けられません(`dip_mcp/logic.py:791` のコメントと同じ判断)。C と D は「消したつもりで届く」失敗が見えにくい
  - E は本人が選べ、何が届くかを本人が分かります
  - B は写真を確実に外せる場面(テキストのある PDF)だけに効きます。読み取りの質が落ちないかを、`resume_intake/samples` で比べてから入れます

#### トークの本文(#4、#5)

- **推奨: 本人の発言を会話に入れる前に、電話、メール、住所らしい所を `[個人情報を削除]` に置き換える。**
  置き換えは `redact_pii(text, extra=address_spans)`(相談のまとめと同じ決まり。`dip_mcp/logic.py:1124`)で、`turn.accept` の中で行う
- 理由: aica は電話、メール、住所を使いません。LINE の共通ルールも聞き出さない決まりです(`line_runtime/agent.py:28`)。
  伏せれば、LLM にも会話の保存にも届きません
- 画面: 伏せたときは、本人の吹き出しに「電話番号などは送らないようにしました」と小さく出す。本人が書いた文と保存された文が違う理由が分かるようにする
- 氏名は伏せられません。同意の文言と入力欄の近くの注意で「名前は書かないで」と示します

#### system prompt の LINE のユーザーID(#7)

- **推奨: system prompt からユーザーIDを外し、「ツールの `line_user_id` には `me` を入れる」と書く。**
- 理由: `PinUserMiddleware` が、ツールの `line_user_id` を会話のユーザーに置き換えます(`line_runtime/agent.py:79-95`)。
  LLM が本当の ID を知る必要はありません。固定の文になるので、プロンプトキャッシュも壊しません
- 気をつけること: ツールの結果に ID が入っていれば、それは LLM に届きます。結果に ID を返すツールが無いかを、実装の task で確かめます

#### 音声(#10〜#12)

- 声と文字起こしは、相談そのものなので送らざるを得ません。先方に残る量を減らします
- **推奨**
  - Deepgram: `mip_opt_out=true` を付ける。割引がなくなる分の費用は、LLD の 7.2 の見積もりに足す
  - LiveKit: `session.start(..., record=False)` を付ける(`voice_resume/agent.py:132`)。LiveKit Cloud のプロジェクトの設定でも録音を切る
  - LiveKit のプラン: 前の推奨は「公開では有料プランにする」でした。無料プランでは匿名化したデータを turn detector の改善に長く残すことがある、と見たためです。
    **決定(利用者): 無料の Build プランのまま。** その記述は公式ページで確かめられなかった(未確認)ので、ポリシーには書きません(2.2、「利用者の決定」)。
    Build プランは毎月の無料の枠が上限で、超えても請求されません。Agent Observability が有効だと、録音と文字起こしがセッションの後 30 日残ります。
    録音は `record=False` で止めます(jyoka/tasks#209)
  - Cartesia: 送る文はアドバイザーの文ですが、本人の話をくり返すことがあります(2.1 の #12)。**公開の前に、Cartesia の規約で、API で受けた文を学習に使うかと保持の期間を確かめる。**
    学習に使わないと確かめられたら既定のまま使います。使う、または分からないなら、ポリシー 5 にそう書くか、Zero Data Retention(エンタープライズの契約)か別の読み上げに替えるかを人が決めます。
    **決定(利用者): 確かめずに、そのまま使う。** ポリシー 5 には、学習と保持は Cartesia の決まりにより、運営者は確かめていないと書きました
  - STT の提供元: **本番では Deepgram に固定する(`VOICE_RESUME_STT_PROVIDER=deepgram`、既定のまま)。** `openai` にすると声そのものが OpenAI に届きます(2.1 の #10)。
    `openai` に替えるなら、ポリシー 5 の OpenAI の「送る情報」に「声」を足し、音声相談の同意の文言も直します
- LiveKit の参加者の metadata の `user_id` は、匿名ユーザーIDのままにします。名前ではなく、ワーカーがどのユーザーかを知るのに要るためです

#### OpenAI の呼び出し全般

- **推奨: Responses API を使う呼び出しは、すべて `store=False` にする。** 対象は、エージェント(`ChatOpenAI(use_responses_api=True)`、`line_runtime/agent.py:101-102`)、
  履歴書の読み取り(`resume_intake/extract.py:94`)、下書き(`voice_resume/drafter.py:34`)、調べもの(`voice_resume/advisor.py:730`)
- エージェントは、前の応答の ID を使わず、毎ターン会話の全文を送っているので、`store=False` にしても動きは変わらないはずです(実装の task で確かめる)
  - ただし、reasoning のあるモデルで `store=False` にすると、前のターンの reasoning の項目を ID で送り直せず、2 ターン目で失敗することがあります(推測。確かめていない)。
    そのときは `include=["reasoning.encrypted_content"]` を付けるか、reasoning の項目を送り直さないようにします。task 2 で 2 ターン以上の会話を通して確かめます
- Zero Data Retention は審査と追加の条件があるので、人が申し込むかを決めます

#### 調べものの問い(#13)

- **推奨: `web_research` と `research_company` の問いに電話、メール、住所らしい所があれば、検索せずに「個人情報を含むので調べない」と返す。**
- 理由: 今は、ツールの説明で「個人情報は入れない」と頼んでいるだけです(`voice_resume/advisor.py:432`)。検索の問いは LLM の事業者(task 236 から既定は Anthropic)を通って検索エンジンにも届きます

### 3.3 保存する範囲、期間、消し方

#### 期間

| データ | 残す理由 | 推奨の期間 | 消し方 |
|---|---|---|---|
| 会話(`data/line_checkpoints.db`) | 30 分以内の続きと、前の問いのボタンの答えの続き(conversation-layer.md §4.16)、画面の描き直し。問い合わせと不正利用の調べ | 会話(`thread_id`)ごとに、最後のやりとりから 30 日 | 掃除が `checkpoints` と `writes` の行を消し、VACUUM する |
| dip の状態のユーザー(`data/state.json`) | 次の相談で希望とまとめを引き継ぐ | 最後の利用から 180 日 | 掃除がユーザーの行を丸ごと外す。「すべて消す」と違い、持ち越す値も残さない(下の「消し方」) |
| 履歴書の読み取り結果 | 同上 | ユーザーと同じ(180 日) | 同上 |
| 音声相談のファイル(`data/voice-resume/`) | 下書きを作るまでの入力。運営者の調べもの | 本番では書き出さない | 書き出しを設定で止める(既定は止める。開発のときだけ書く) |
| 費用台帳(`data/costs.jsonl`) | 費用を人ごと、日ごとに数える | ユーザーIDは 90 日。過ぎたら日ごとの合計だけ残す | 掃除が 90 日を過ぎた行を日ごとの合計の行に置き換える |
| ターン数(`data/quota.json`) | その日の上限 | 今のまま(日付が変わると数え直す) | - |
| Cookie `aica_uid` | 同じブラウザを同じ人として扱う | 最後に画面を開いた日から 180 日(ユーザーの期間に合わせる) | `ANON_COOKIE_MAX_AGE` を 180 日にし、画面を開くたびに同じ ID で Cookie を書き直して期限を延ばす(下の注) |
| 連携の表(`data/dip_accounts.db`) | 連携している間、dip の会員を引く | 連携の間。ユーザーを消すときに外す | 今のまま(`State.reset_user` が外す) |
| アクセスログ、アプリのログ | 障害と不正利用の調べ | ホスティングの保持に任せ、30 日以内の設定にする | ホスティングの設定(Render の保持は要確認) |
| バックアップ | 壊れたときの戻し | 7 日 | 消したものも、バックアップから 7 日以内に消える、とポリシーに書く |

- 「最後の利用」は、ターン、プロフィールの操作、音声相談の結果のどれかの最後の時刻です。dip の状態に `last_seen_at` を足して記録します
- Cookie の期限は、定数を変えるだけでは「最後の利用から」になりません
  - 今の `_issue` は、Cookie が無いときにしか `set_cookie` を呼びません(`line_runtime/server.py:107-115`)。なので期限は「最初の発行から」数えます
  - 定数だけを 180 日にすると、毎日使う人でも 181 日目に Cookie が切れ、新しい `w-…` になります。前の希望とまとめは引き継げず、古い ID のデータは本人が開けないまま、さらに 180 日残ります
  - **推奨: `_issue` は、Cookie があって形式が正しいときも、同じ ID で `set_cookie` を呼び直す。** 呼ぶのは画面を開いたとき(`GET /` と `GET /dev`)です。API は今のまま書き直しません
  - 理由: トーク画面は開いたまま何日も使うことは少なく、使うたびにまず `GET /` を通ります。画面を開いた時刻で延ばせば、「最後の利用から 180 日」とほぼ同じになります。API の応答ごとに書き直すより、変える所が 1 か所で済みます
  - ずれ: 画面を開いたまま 180 日を超えて使い続けると、その間に期限が来ます。現実には起きにくいので受け入れます
- 期間の数の理由
  - 30 日(会話): 会話は 30 分空くと切れ、次の会話は dip の要約から始まります(HLD の 4.8)。古い会話を機能に使うのは、前の問いのボタンの答えを
    続けるときだけです(この期間が上限。conversation-layer.md §4.16)。問い合わせや不正利用の調べにも 1 か月は要ると見ました
  - 180 日(ユーザー): アルバイト探しは数週間、正社員の転職は数か月かかるので、その間の再訪で前の希望を引き継げる長さです。
    数は推測で、使われ方を見て変えてよい値です
  - 90 日(費用台帳): 月ごとの費用の確認と、前の月との比較に足りる長さです
- 会話の期間の案は 3 つ比べました
  - 案 1: 期限なし(今)。消すのは本人だけ
  - 案 2: 会話ごとに最後のやりとりから 30 日(推奨)
  - 案 3: 新しい会話を始めたら前の会話をすぐ消す。一番短いが、問い合わせのときに何も残らない
  - 案 2 にしたのは、案 3 との差が「問い合わせに答えられるか」だけで、その差に 30 日の保持が見合うと見たからです

#### 消し方

- 掃除を 1 つのモジュールにまとめ、いつも Web プロセスの中で走らせる。呼ぶのは、Web プロセスの起動時と 1 日 1 回の定期実行と、手で走らせる CLI(`python -m line_runtime.purge`)
- ユーザーを消すときは、`server.profile_forget` と同じ順番にする。会話を消してから dip の状態を消し、音声のファイルを消す。
  ターンの排他(`user_lock`)の中で行う
- CLI の扱い: `user_lock` は Web プロセスのメモリの `asyncio.Lock` です(`line_runtime/runtime.py:123`、`:190`)。会話の番号のキャッシュ `_threads`(`:124`)と、未読のアップロード `app.state.unread_uploads`(`line_runtime/server.py:811`)も Web プロセスにあります。別プロセスの CLI はどれも触れません。
  CLI が自分で消すと、進んでいるターンが、消す前に読んだ要約を新しいチェックポイントに書き、dip の状態も作り直します。消したはずの内容が残ります
  - 案 a: CLI は Web プロセスを止めているときだけ使う。定期の掃除は Web プロセスの中だけで行う
  - 案 b: CLI は Web プロセスの内部の口(例 `POST /api/internal/purge`)を呼ぶだけにする。口は `AICA_INTERNAL_KEY` で守る(`_require_internal`、`line_runtime/server.py:158`)。消す処理は Web プロセスの中で `user_lock` を取って行う(推奨)
  - 案 b にしたのは、本番の Web プロセスは止めずに動き続けるので、案 a では CLI を使える時がほぼ無いからです。消す道も 1 本になり、`_threads` と `unread_uploads` の片付けも `profile_forget` と同じ所でできます
- SQLite は消した後に VACUUM する。しないと、消した行がファイルの空き領域に残る
- `state.json` は書くたびに全体を書き直すので、消した値はファイルに残らない(`dip_mcp/data.py:213-217`)
  - ただし、ファイルを置き換えた後も、ディスクの空きブロックには古い中身が残りえます。VACUUM の後の SQLite も同じです。Render のディスクが暗号化されているかを、6 章の Render の確認と一緒に見ます
- 掃除のログは件数だけを出す(「会話 12 件、ユーザー 3 人を消した」)

#### 期間で消すときは、ユーザーの行を丸ごと外す

- 今の「すべて消す」の `profile.forget_all`(`dip_mcp/profile.py:286-306`)は、ユーザーの行を消し切りません
  - `state.reset_user` の後、同じユーザーIDの行に `_KEPT_ON_FORGET`(`dip_mcp/profile.py:283`)の連番と `forgotten_voice_rooms` を書き戻します(`:296-305`)
  - 例: 架空の `w-0000000000000000` に音声の部屋が 1 つある状態で `forget_all` を呼ぶと、`state.json` の `users` にそのIDの行が `forgotten_voice_rooms` つきで残ります
  - なので、期間で消す掃除が `forget_all` をそのまま呼ぶと、180 日を過ぎたユーザーの行がいつまでも残ります
- **推奨: 期間で消す掃除は `forget_all` を使わず、ユーザーの行を丸ごと外す。**
  - 外すのは、そのユーザーと、同じブラウザのシナリオ用ユーザー(`{ID}:…`)の行です。`state.json` の `users` から外し、連携の表(`data/dip_accounts.db`)も外します。会話、音声のファイル、`_threads`、`unread_uploads` は `profile_forget` と同じ順番で片付けます
  - 持ち越す値も残しません。理由: 180 日も使われていなければ、消す前に始めた音声相談の結果が後から届くことはありません(部屋のトークンの期限は 5 分、`voice_resume/livekit_token.py:19`)。古いリンクの番号がぶつかる心配も、Cookie が同じ 180 日で切れるのでほぼありません
  - fixtures のユーザーそのもの(評価用の架空のユーザー、例 `sim-new`)は掃除しません。個人情報ではなく、消すと評価が壊れるためです
- 本人が「すべて消す」をしたときに持ち越す行は、残す理由と期限を決める
  - 残す理由: `forgotten_voice_rooms` は、消す前に始めた面談の結果を 410 で断るためです(`line_runtime/server.py:899-903`)。連番は、古いリンクが消した後の新しい履歴書や下書きを開かないためです
  - **推奨: 「すべて消す」で `last_seen_at` を消した時刻にする。掃除は `forgotten_voice_rooms` を、消した時刻から 1 日で外す。連番は、行と一緒に 180 日で外す。**
  - 1 日の理由: トークンの期限は 5 分ですが、面談そのものの長さの上限はコードに見当たりませんでした。1 日あれば、続いている面談の結果も断れると見ました(推測)。task 7 で、面談の長さの上限を足すか確かめます
  - この形なら、持ち越した行にも `last_seen_at` があるので、掃除が 180 日で丸ごと外せます
- `last_seen_at` が無い行(task 7 を入れる前からある行)は、task 7 を入れた時刻を `last_seen_at` とみなします。いきなり消さず、そこから 180 日で消えます

#### 「すべて消す」の後に残るもの
