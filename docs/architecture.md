## 段階: ベータ

ベータとします。

- 実ユーザー(求職者)が使います(このカードの前提。利用者の数はリポジトリから分からない)。止まると、相談の途中の人が困ります
- 利用規約の第 1 条の 2 で、商用ではなくテストのための公開としています
- 止まる時間や失うデータの上限は約束していません。利用規約の第 8 条で、事前の知らせなく止めることがあると書いています
- 求人は架空のデモの求人です(利用規約の第 1 条の 4)。応募しても実際の応募にはならず、止まっても採用の機会は失われません

本番に上げるきっかけは次のどれかです。

- 実在の求人や企業とつなぐ
- 有料にする、または止まる時間を約束する
- 企業や自治体などの取引先に、運用の約束を求められる

## メモリ不足とダウンへの今の対応

結論: Render が自動で起動し直す仕組みはありますが、**すぐに気づく仕組みはありません**。
対応の手順は [runbook](deploy/runbook.md) に書きました。担当は運営者 1 人(jyoka)です。戻し方は試していません。
Render の通知は設定待ちです。設定するまでは、ダウンにもメモリ不足にも、運営者がダッシュボードを開くまで気づけません。
設定した後も、メモリ不足そのものは通知の一覧にありません。
メモリ不足とインスタンスの失敗は、運営者が毎日 1 回数えることにしました(関門 6。始める前)。気づくのは最大 1 日遅れます。

### 起きたこと

- 2026-10-27 に、`aica` のコンテナが待機中だけで 2GB のうち 1.83GB を使っていました(コミット `04ab6b3`)。
  音声ワーカー(turn detector の推論 約 820MB と、温めておく相談のプロセス)が同じコンテナにいたためです
- メモリ不足で落ちた日時と回数は、リポジトリに記録がありません(未確認。Render の「Events」で見られる)
- 対策の途中です。音声ワーカーを `aica-voice` に分ける 1 つ目の PR は main に入りました。
  2 つ目の PR(`aica` の `AICA_VOICE_WORKER` を `0` にする)はまだです。Render の上で `aica-voice` が相談を受けているかは未確認です
- 移す間の `aica` は、待機だけで約 1.6〜1.7GB の見込みです。`aica` の音声ワーカーが 2 件を同時に受けると、2GB を超えることがあります
  ([docs/deploy/render.md](deploy/render.md#1-つのコンテナで動かしていたサービスを分ける-運営者))

### 落ちたときの影響と自動の復旧

| 落ちるもの | 影響 | 自動の復旧 |
|---|---|---|
| `aica` のコンテナ全体(2GB を超える、Web プロセスが終わる) | トーク、履歴書、ゲーム、LINE の webhook、dip がすべて止まる。台数は 1 なので代わりはない。進行中のターンは失われる。プロセスのメモリにある状態(ターンの排他、音声相談の待ち合わせ、読み取れなかったアップロード)も消える。ディスクのデータは残る | Render が起動し直す。Render の文書では、メモリ不足のとき `Out of memory` のイベントが、終わったインスタンスに `Instance Failed` のイベントが出る。起動し直すまでの時間は測っていない |
| `aica` の Web プロセスが固まる(生きているが答えない) | 上と同じ | `/healthz` が 15 秒続けて失敗すると Render が要求を止め、60 秒続けて失敗すると起動し直す(Render の [Health Checks](https://render.com/docs/health-checks))。`/healthz` は起動を終えていれば 200 を返すだけで、ディスクや dip は見ない |
| `aica` のコンテナの中の音声ワーカー | `aica-voice` が相談を受けていれば、相談は続く。トークは動く | `scripts/container_start.sh` のループが 10 秒後に起動し直す |
| `aica` のコンテナの中の dip の MCP サーバー | `aica-voice` の相談は、dip の道具なしで続く(呼び出しは 15 秒で諦める)。トークは動く | 同じく 10 秒後に起動し直す |
| `aica-voice` | 移す間は `aica` の音声ワーカーが相談を受ける。移し終えた後は音声相談が止まる | プロセスが終われば Render が起動し直す(と render.md に書いてある。本番では確かめていない)。ヘルスチェックはないので、固まったときは起動し直さない |
| 音声相談 1 件のプロセスが上限を超える | その相談だけが止まる | livekit-agents が止める。上限は `aica-voice` で 400MB、`aica` で 2000MB(既定) |
| デプロイ、環境変数の保存 | 止まる。ディスクつきなので、古いインスタンスを止めてから新しいものを起動する。Render の文書では数秒で、測っていない。進行中のターンは、Web プロセスが終えてから止まる(`Dockerfile` の tini)。音声相談は切れる | - |
| 鍵の入れ間違い、鍵の不足 | `ANTHROPIC_API_KEY` が無いと、Web プロセスは起動の途中で止まる。`LIVEKIT_*` があるのに `AICA_INTERNAL_KEY` が無いか短いと、Web プロセスも音声ワーカーも起動で止まる | Render が起動し直しても、鍵を直すまで動かないはず(確かめていない) |
| ディスクの中身が壊れる、消える | 会話、プロフィール、同意、費用台帳がすべて失われる | Render のスナップショット(7 日)から戻せるはず。戻すと、その後の変更は消える。試していない |

### 足りない点

- ダウンに、運営者が数分のうちに気づく仕組みがない(関門 6)。外形監視は入れたが、15 分ごとで、設定待ち。メモリ不足は、毎日の点検で 1 日のうちに気づく(始める前)
- `aica` は Web と音声ワーカーが同じコンテナにいる間、音声の負荷で Web も落ちうる(関門 3)
- `aica-voice` が固まったことに気づけない(関門 3、6)
- 落ちたときの手順は [runbook](deploy/runbook.md) に書いたが、戻し方を 1 つも試していない(関門 4、6)。対応できる人は運営者 1 人だけ
- 復元を試したバックアップがない(関門 0)

## 0. 基盤リソース

- 決定: Render の 2 つのサービス(`aica`、`aica-voice`、どちらも Singapore)と、`aica` の永続ディスク 2GB だけを使う。
  データは SQLite と JSON のファイルでディスクに置き、マネージド DB は使わない。バックアップは Render のディスクのスナップショットに任せる。
  環境は本番 1 つと手元だけで、検証の環境はない。
  データが消えると、全員の会話、プロフィール、同意の記録、費用台帳が失われる。求人は架空なので、採用の機会は失われない
- 理由: Web プロセスは 1 つだけで動かす作り(ターンの排他やターン数の上限をプロセスとファイルで持つ。[review-2026-10.md の R12](architecture/review-2026-10.md#r12-web-プロセスのメモリに状態があり1-プロセスでしか動かない))で、
  ファイルを 1 つのディスクに置けば足りる。DB を分ける理由はまだない
- 見直すきっかけ: ディスクの使用が 80% を超えたとき(Render の通知)。Web を 2 台以上にしたくなったとき。
  スナップショットからの復元が使えないと分かったとき。dip の状態の JSON(R8)が重くなったとき
- 路線とコスト: マネージド有料(Render のディスク)。月額は Render の料金ページで確かめる。払う理由: ディスクの保持と日ごとのスナップショットを任せたい
- ベータの最低要件との差: バックアップの復元を試していない。SQLite を開いたままのスナップショットで中身がそろうかは確かめていない(Render の文書は、MySQL などの DB を置いたディスクでは、DB を直すためにディスクを戻さないよう書いている)。
  Render と GitHub の権限(誰がダッシュボードと鍵を見られるか)は未確認

## 1. IaC

- 決定: Render の Blueprint(`render.yaml`)で、2 つのサービス、ディスク、ヘルスチェック、環境変数の名前を書く。Terraform などは使わない。
  Auto Sync は有効にする手順で(ダッシュボードの状態は未確認)、`render.yaml` を変えた PR を main に入れるとそのまま本番に入る
- 理由: Render のリソースは Blueprint で足りる。ほかの道具を足すと、同じものを 2 か所で持つことになる
- 見直すきっかけ: Render の外のリソース(DB、監視、外部のストレージ)を足すとき。検証の環境を作るとき
- 路線とコスト: マネージド(PaaS の設定ファイル)。Blueprint そのものに追加の料金はない(未確認)
- ベータの最低要件との差: Blueprint で同じ環境をもう一度作れる。ただし、次はコードの外にある。
  鍵の値(`sync: false`)、Render の通知の設定、LiveKit、Deepgram、Cartesia、LINE のアカウントとプロジェクト

## 2. パッケージング

- 決定: 1 つの `Dockerfile`(`python:3.12-slim`)を、2 つのサービスがそれぞれ build する。
  `aica-voice` だけ、build の引数 `AICA_VOICE_MODELS=1` で音声のモデル(約 460MB)を image に入れる。
  build は Render が、「Manual Deploy」と `render.yaml` の同期のときにする。デプロイしないコミットの image はない。
  image の置き場所は Render の中で、自分のレジストリは持たない
- 理由: Render の Docker の build に任せれば、レジストリを持たずに済む。検証の環境がなく、同じ image を流す先がない
- 見直すきっかけ: 検証の環境を作り、同じ image を検証から本番へ流したくなったとき。build が遅い、失敗することが続いたとき
- 路線とコスト: マネージド(Render の build)。サービスの料金に含まれる(未確認)
- ベータの最低要件との差: `requirements.txt` は `>=` の範囲だけで、lockfile がない。build のたびに依存の版が変わりうるので、
  POC の要件(依存の版を lockfile で固定する)も満たしていない

## 3. 実行と編成

- 決定: Render の上で、`aica` を 1 台、`aica-voice` を 1 台で動かす。冗長化とフェイルオーバーはしない。
  落ちたら Render が起動し直す。`aica` は `/healthz` が 60 秒続けて失敗すると起動し直される。
  `aica` のコンテナの中の音声ワーカーと dip の MCP サーバーは、シェルのループが 10 秒後に起動し直す。
  メモリの上限はサービスごとに 2GB。音声相談は 1 件ごとに上限があり(`aica-voice` で 400MB)、超えるとその相談だけを止める。
  `aica` の Web プロセスには上限がなく、コンテナ全体が 2GB を超えると Web も止まる。
  落ちたときの影響と復旧は、上の「[落ちたときの影響と自動の復旧](#落ちたときの影響と自動の復旧)」の表のとおり。
  自動で戻らないときの手順(起動し直す、前のデプロイに戻す、`aica-voice` の Suspend、鍵の入れ直し)は [runbook](deploy/runbook.md) にある
- 理由: 永続ディスクは 1 つのインスタンスにしかつながらない。ターン数の上限とターンの排他を 1 つのプロセスで持つ(R12)。
  音声ワーカーを別サービスにしたのは、相談の数だけ増えるメモリで Web も一緒に落ちないようにするため
- 見直すきっかけ: メモリ不足で落ちたことが、移し終えた後にもう 1 回でもあったとき。
  止まる時間を約束するとき(本番)。同時に話す人が増え、1 台で返事が遅くなったとき。`aica` を Starter(512MB)に下げるとき
- 路線とコスト: マネージド有料(Render の Standard を 2 つ)。月額は Render の料金ページで確かめる。
  払う理由: サーバーの更新と、落ちたときに起動し直すことを任せたい。音声ワーカーは待機だけで約 1.4GB(turn detector の推論が約 820MB)なので、2GB のプランが要る
- ベータの最低要件との差: 自動で起動し直す仕組みとヘルスチェックは `aica` にある。`aica-voice` にはヘルスチェックがない。
  `aica` は、移す間は音声の負荷で Web も落ちうる(移し終えれば解ける)。相談中のプロセスが 400MB に収まるかは測っていない

## 4. CI/CD

- 決定: PR と main への push で、GitHub Actions が pytest、ruff、`evals.baito_sim` を回す(実 API なし)。
  デプロイは、運営者がダッシュボードの「Manual Deploy」でする(`autoDeployTrigger: "off"`)。`render.yaml` の変更だけは、
  main に入ると Auto Sync で入る。デプロイの後に `scripts.deploy_smoke --url` で確かめる(実 API を 1 回使う)
- 理由: デプロイすると止まり、相談中の人の音声が切れる。相談の少ない時間を選び、すぐに確かめたい
  (render.md の Auto Sync の注意から。自動デプロイを off にした理由そのものは、コミットに書かれていない)
- 見直すきっかけ: デプロイの回数が増え、手の操作を忘れることがあったとき。デプロイで壊れたことが 1 回でもあったとき
- 路線とコスト: 無料(GitHub Actions の無料枠)と、Render のデプロイ(サービスの料金に含まれる)
- ベータの最低要件との差: PR ごとのテストと、ダッシュボードの 1 操作のデプロイはある。
  戻し方はリポジトリに書いていない(Render のダッシュボードで前のデプロイに戻せるはずだが、確かめていない)。
  CI が落ちたコミットも「Manual Deploy」で入れられる(本番の要件。ベータでは求めない)

## 5. 設定と秘密情報

- 決定: 秘密情報は Render の環境変数にだけ置く。
  - 運営者が Blueprint を作るときにダッシュボードで入れる: `ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`LIVEKIT_URL`、`LIVEKIT_API_KEY`、`LIVEKIT_API_SECRET`、`DEEPGRAM_API_KEY`、`CARTESIA_API_KEY`(`sync: false`)
  - Blueprint が作る: `AICA_INTERNAL_KEY`(`generateValue`)
  - `aica-voice` は `fromService` で `aica` から写す。値は `aica` にだけ入れる。ダッシュボードで入れた値まで写るかは未確認
  - LINE をつなぐときは `LINE_CHANNEL_SECRET`、`LINE_CHANNEL_ACCESS_TOKEN`、`AICA_ID_KEY` を手で足す
  - 手元は `.env` に置く。`.gitignore` と `.dockerignore` が外すので、リポジトリにも image にも入らない
  - CI には秘密情報を渡さない
- 理由: PaaS の環境変数で足りる規模で、保管庫を足す理由がない
- 見直すきっかけ: 運営者が 2 人以上になり、誰が鍵を読めるかを分けたくなったとき。検証の環境を作るとき。鍵が漏れたとき
- 路線とコスト: マネージド(PaaS の環境変数)。追加の料金はない(未確認)
- リポジトリに秘密情報が入っていないか(2026-10-28 に確かめた):
  - 追跡しているファイルに `.env` や鍵のファイルはない(`git ls-files`)
  - 追跡しているファイルと、このリポジトリの全部の履歴(437 コミット)を、Anthropic と OpenAI の鍵の形、AWS の鍵の形、秘密鍵の PEM の形で探し、0 件だった(`git grep`、`git log --all -G`)
  - このリポジトリは旧リポジトリ(`aica_ra_a2a_poc`)から履歴なしで移した。旧リポジトリの履歴は見ていない
  - LiveKit、Deepgram、Cartesia、LINE の鍵は形が決まっておらず、上の探し方では見つからない。これらは探していない
- ベータの最低要件との差: 置き場所(手元は `.env`、本番は Render)は決まっている。漏れたときの差し替えの手順がない。
  鍵ごとに、どこで無効にし、どこに入れ直し、どのサービスを起動し直すかを書く。
  `aica` の値を変えたら `aica-voice` に写し直す手順(Blueprint の「Manual sync」と「Manual Deploy」)は [docs/deploy/render.md](deploy/render.md#環境変数) にある。
  `AICA_ID_KEY` は、変えると全員の LINE のユーザーIDが変わり、それまでのデータとつながらなくなる。
  漏れたら変えて、つながらなくなることを受け入れる([ADR-0008](adr/0008-keyed-line-user-id.md))。
  環境変数を保存すると `aica` は起動し直し、止まる。鍵を入れ間違えると起動で止まる(上の表)。
  dip の子プロセスがすべての環境変数を受け取る(R15)

  - `aica` だけ: unhealthy(`/healthz`)、ディスクの使用の 80% 超え
  - `aica-voice` の unhealthy は未確認(バックグラウンドワーカーには Render のヘルスチェックがない)

  - 未確認: メールがワークスペースの誰に届くか、送り元のアドレス。運営者が試しのサービスで確かめて、ここに書く
  - 設定した日: (設定待ち)
- 決定(外形監視。**設定待ち**): GitHub Actions の `schedule` で、公開 URL の `/healthz` を外から呼ぶ(路線 (a))。
  ワークフローは `.github/workflows/healthz.yml`、判定は `scripts/healthz_watch.py`。手順、止め方、確かめ方は [docs/deploy/render.md の 8](deploy/render.md#8-外形監視を有効にして確かめる-運営者)
  - 間隔: 15 分ごと(毎時 7、22、37、52 分)。1 回の実行の中で 60 秒おきに 3 回まで呼び(1 回の待ちは 10 秒)、3 回続けて 200 以外か時間切れなら落ちているとする
  - 届き方: 落ちたら Issue を開き、リポジトリの持ち主(運営者)に割り当て、その回のジョブを失敗にする。GitHub からメールが届く。
    落ちている間は Issue を開き直さず、ジョブも失敗にしない(同じ障害で何度も知らせない)。回復したら Issue を閉じる。
    閉じて 24 時間のうちにまた落ちたら、新しく開かずに閉じた Issue を開き直す(メモリ不足で落ちては戻るを繰り返しても Issue が増えない)
  - 監視そのものが止まったとき(Actions の分数が尽きた、`schedule` の回が落とされた)は、知らせが届かない
  - 公開 URL はリポジトリの変数 `AICA_HEALTHZ_URL` に置く。`secrets.*` は使わない。Issue は Actions が実行ごとに作る `github.token` で開く
  - 知らせが届くまでの目安(推測。測っていない): 落ちてから平均 10 分前後、遅くとも 20 分ほど。
    内訳は、次の回まで最大 15 分、判定に約 2〜3 分、runner の起動とメールで 1 分ほど。
    GitHub の `schedule` は混むと遅れ(毎時 0 分が混む)、その回が落とされることもある。遅れの上限を GitHub は約束していない。1 回落とされると 15 分延びる
  - 間隔の下限: GitHub の `schedule` は 5 分ごとが下限。5 分にしても、上の遅れは残る
  - 設定した日: (設定待ち。運営者が変数を入れ、render.md の 8 で Issue とメールが届くことを確かめて書く)
- 決定(メモリ不足。**始める前**。task 322): 運営者が毎日 1 回、手元の Mac で `scripts.render_events` を動かし、Render の API から
  `aica` と `aica-voice` のメモリ不足(`Out of memory`)とインスタンスの失敗(`Instance Failed`)を、直近 24 時間と 7 日で数える。
  回数で、記録するだけか、その日のうちに原因を見るかを決める。手順と回数の決まりは [docs/deploy/render.md の 7](deploy/render.md#7-メモリ不足とインスタンスの失敗を毎日見る-運営者)

  - 鍵がないときと API が答えないときは、同じ回数の決まりで、ダッシュボードの「Events」を見る
  - 知らせの仕組み(届く通知)は作らない。気づくのは最大 1 日遅れる
  - 始めた日: (始める前)

- 理由: エラーの記録は、決めていなかった(決めた記録がリポジトリにない)。ベータとしては足りない。
  通知をメールにしたのは、失敗の通知はすべてメールで届き、Slack でしか届かないもの(デプロイの成功、回復)は気づくために要らないため。

  - 追加の契約とアカウントが要らない。リポジトリの中で完結し、PR で変えられる。判定をテストできる(`tests/test_healthz_watch.py`)

  - コマンドにしたのは、2 つのサービスのメモリ不足とそれ以外の失敗を 1 回で数え、回数の決まりをテストで固定するため。

## 確かめていないこと

- Render のダッシュボードの中身: サービスが `render.yaml` のとおりか、Auto Sync が有効か、`aica-voice` に鍵が写っているか、`aica-voice` が動いているか、通知の今の設定、Events に残るメモリ不足の日時と回数、ワークスペースの権限、ワークスペースのプラン(Hobby か Pro 以上か)
- Render の API でのメモリ不足の出来事の形: ダッシュボードの `Out of memory` と `Instance Failed` が、API でどちらも `server_failed` になり、メモリ不足のときだけ `details.reason.oomKilled` が付くこと
  (API の型からの読み。本番の出来事でも、Render の文書でも確かめていない)。API が出来事を何日残すか。Hobby のワークスペースで API を使えるか
- Render の通知のメールが、ワークスペースの誰に届くか。送り元のアドレス。`aica-voice` で unhealthy の通知が出るか
- 外形監視の知らせ: GitHub のメールが Render の通知と同じアドレスに届くか。schedule の回の失敗のメールが誰に届くか(cron を最後に変えた人)。
  実際の `schedule` の遅れの大きさ。GitHub アカウントのプランと、Actions の分数の残り
- メモリ不足で落ちた後に、Render が起動し直すまでの時間
- `aica-voice` のプロセスが終わったとき、Render が起動し直すか(render.md にはそう書いてあるが、本番では確かめていない)
- Render のスナップショットから、SQLite のファイルが壊れずに戻るか
- Render のログの保持の期間
- 各サービスの月額
- 独自ドメインを使っているか(`render.yaml` にはない)
- LINE 公式アカウントを本番につないでいるか
