# PRD: aica v2 - 正社員までカバーし、発話から雇用区分を切り替え、相談を深くする

設計の経緯: jyoka/tasks#94(2026-09-27、ユーザーとの対話で決定)。用語は [CONTEXT.md](../../CONTEXT.md)、後から覆しにくい判断は [ADR-0001](../adr/0001-track-and-playbook-as-dip-tools.md)・[ADR-0002](../adr/0002-one-job-model-with-employment-type.md)。親 PRD は jyoka/tasks#54(aica v1)。

## Problem Statement

2026-09-27 に運営者が自分の職務経歴書(PM・法人営業・多言語、正社員の経歴)で aica を試したところ、次のことが起きた。

- 相談モードに入っても、経歴と関係のない選択肢(「人と話す仕事 / 事務や運営を支える仕事」、その後「オフィス事務 / コールセンター / イベントスタッフ」)が出た。求人データがアルバイトの12職種しか無く、Prompt が「職種の一覧から2〜3つ挙げる」よう指示しているため、経歴を無理にアルバイトの職種へ結びつけた
- ヒアリングが浅い。項目(経験 → 興味 → 不安 → 生活の制約)を1問ずつ埋めるだけで、「なぜ今探すのか(目的)」を聞く項目が無く、答えを掘り下げない。「まだ分からない」と答えるとすぐ職種の列挙に移った。本人が逆に質問してはじめて軌道修正された
- チャットで話した相談の中身(「経験を活かしたい」)はどこにも保存されず、音声相談に引き継がれなかった(履歴書が音声に渡らないバグは PR jyoka/aica#10 で修正済み)
- 評価ではこの浅さを拾えなかった。模擬ユーザーが全員新規・未経験寄りで、判定も形式(1問ずつ・聞き直さない)しか見ていなかった
- 意味検索(#28 から移植)は、言い換えの質が低い。「人と話さず黙々と」でコールセンターが出て、「体を動かしたい」は0件。類似度の下限 0.30 が正解(倉庫・軽作業 0.228 など)を落としている

求職者はアルバイトだけを探しているとは限らない。経歴のある人が転職で正社員を探すこともあれば、正社員の人が副業でアルバイトを探すこともある。aica は、本人の話から「これから何を探したいのか」をつかんで、その探し方に合った相談と提案をする必要がある。

## Solution

- **正社員の領域をカバーする**: 求人に雇用区分を持たせ(ADR-0002)、架空の正社員求人を用意し、検索・カード・保存・応募を両方の区分で動かす
- **雇用区分を発話から切り替える**: 本人の発話から「アルバイト・パート / 正社員 / 未定」を判断し、dip のツール `set_search_track` で切り替えて記録する(ADR-0001)。切り替えは本人に見え、取り消せる
- **相談を深くする**: 区分とチャネル(チャット・音声)ごとの playbook に「明らかにすること」と「掘り下げ方」を書き、`get_counseling_playbook` で配る。目的を必ず聞き、目的とやりたいことを掘り下げ、選択肢を本人の履歴書と発言から作る
- **チャットと音声で同じプロフィールを使う**: 保存項目を増やし(目的・強み・やりたいこと・避けたいこと・不安、正社員の条件)、会話を締めるときに「相談のまとめ」を残す。チャットも音声も同じ要約を読む
- **評価で深さと切り替えを測る**: 経歴の厚い人などのペルソナを足し、切り替えはツールの呼び出しで、深さは LLM ジャッジで測る。実 API の予算は $5
- **検索の質を測って直す**: 正解つきの検索評価セットで、embedding の設定を選び直す

UX の刷新(本番はトーク1画面、履歴書・音声を会話の中へ、プロフィール画面、区分の切り替えの表示)は、この PRD と並行して進めている(下の「関連タスク」)。

## User Stories

### 雇用区分
1. As a 転職を考えている求職者, I want 「正社員で探したい」「転職を考えている」と話すだけで正社員の相談に切り替わる, so that 探し方を最初に選ばなくてよい
2. As a 正社員として働きながら副業を探す求職者, I want 経歴が厚くても、本人が「空いた時間にバイトを」と言えばアルバイトで探してもらえる, so that 履歴書から勝手に決めつけられない
3. As a 迷っている求職者, I want 「経験を活かしたい」のような曖昧な話には「正社員の仕事と、空いた時間のアルバイト、どちらを考えていますか?」と1問で確かめてもらえる, so that 取り違えられない
4. As a 求職者, I want 区分が切り替わったことが見えて、ボタン1つで戻せる, so that 自分の意図と違えばすぐ直せる
5. As a 再訪した求職者, I want 前回の区分から始まる, so that 毎回言い直さなくてよい

### 相談の深さ
6. As a 正社員を探す求職者, I want なぜ今探すのか・今の仕事の何を変えたいのかを聞いてもらえる, so that 条件だけでなく目的に合った提案になる
7. As a 相談中の求職者, I want 答えに「それはなぜですか」「具体的にはどんな場面ですか」と1回は掘り下げてもらえる, so that 自分でも言葉にできていなかったことが整理される
8. As a 履歴書をアップロードした求職者, I want 選択肢が自分の経歴と発言から作られる, so that 関係のない一般論の選択肢で時間を使わない
9. As a 「まだ分からない」と答えた求職者, I want 職種の一覧を並べられるのでなく、掘り下げの問いに戻ってもらえる, so that 無理に決めさせられない
10. As a 正社員を探す求職者, I want 吹き出しが短すぎず、じっくり話せる, so that キャリアの相談らしい会話になる

### 正社員の求人
11. As a 正社員を探す求職者, I want 年収の幅・働き方(リモート・残業)・休日・必須と歓迎の経験がカードと回答に出る, so that 応募を判断できる
12. As a 正社員を探す求職者, I want 希望年収の下限・働き方で絞れる, so that 条件に合わない求人を見なくてよい
13. As a 区分が未定の求職者, I want 両方の区分から提案を受けられる, so that 比べながら決められる
14. As a 求職者, I want 言い換え(「人と話さず黙々と」「体を動かしたい」「経験を活かせる仕事」)でも意図どおりの求人が出る, so that 正確な職種名を知らなくても探せる

### チャットと音声の引き継ぎ
15. As a チャットで相談した求職者, I want 音声相談が、チャットで話した目的・希望・履歴書を踏まえて始まる, so that 同じことを話し直さなくてよい
16. As a 音声で相談した求職者, I want 次のチャットが、音声で話した内容の続きから始まる, so that チャネルをまたいでも会話がつながる
17. As a 正社員を探す求職者, I want 音声相談で職務経歴書の下書き(職務要約・成果)ができる, so that 応募書類の準備が進む
18. As a アルバイトを探す求職者, I want 音声相談で今までどおり履歴書の下書きができる, so that 手間なく応募できる

### 運営者
19. As a 運営者, I want 区分の切り替えを評価でツールの呼び出しとして機械判定できる, so that 正規表現の許可リストの誤判定の往復をしなくてよい
20. As a 運営者, I want 相談の深さ(目的を聞いたか・掘り下げたか・選択肢が本人由来か・提案理由が本人の話とつながるか)を根拠つきで測れる, so that 浅さを数字で追える
21. As a 運営者, I want 実 API の費用が PRD 全体で $5 に収まり、$4 に達したら止まる, so that 予算を超えない
22. As a 運営者, I want 検索の質を、正解つきの評価セットの再現率で比べられる, so that embedding の設定を根拠をもって選べる

## Implementation Decisions

### 雇用区分と切り替え(ADR-0001)
- 雇用区分は「アルバイト・パート」「正社員」「未定」の3つ。初回は未定。契約社員・派遣は正社員の派生として後で足す
- 目的(副業・スキル活用・生活費・転職など)は区分とは別の軸で、相談で聞き取って保存する
- 切り替えの合図: 明示(「正社員で探したい」「転職を考えている」)と強い合図(年収・キャリア・転職時期の話 → 正社員、シフト・時給・学校との両立 → アルバイト)は1回で切り替える。弱い・混在した合図は切り替えずに1問で確かめる。履歴書の内容だけでは切り替えない
- dip のツール `set_search_track(line_user_id, track, evidence)`: evidence は本人の発言そのまま。切り替えの履歴(いつ・どの発言で・取り消しか)を dip に記録し、`get_user_conversation_summary` に今の区分を載せる。取り消しも同じツールで記録する(画面のボタンから)
- 区分が変わったターンで、チャットも音声も `get_counseling_playbook` を読み直す
- 会話の段階(相談・提案・支援・待つ)はツールにしない。「モード」という語は使わない

### 求人(ADR-0002)
- 求人に `employment_type` を足し、給与は `pay {kind: 時給|月給|年収, min, max}`。`hourly_wage` は `pay` に移す
- 正社員だけの任意項目: 必須・歓迎の経験、働き方(リモート可・フレックス・残業の目安)、休日(年間休日・土日祝)、雇用の条件(試用期間など)
- 職種の一覧は区分ごとに別。アルバイトは今の12種、正社員は10種前後(営業、企画・PM、エンジニア、事務・管理、販売・サービス、製造・技術、医療・介護、教育、クリエイティブ、物流 などを実装タスクで確定)。区分ごとに完全一致
- 架空の正社員求人を40件ほど、今と同じエリアに置く。経歴の厚い人(PM・法人営業・多言語)に合う求人を含める。すべて架空
- `recommend_jobs` に `employment_type` と `min_annual_salary`。区分が未定なら両方から出してよい。`answer_job_question` の資料と、評価の事実照合を `pay` に合わせる

### 検索の質
- 正解つきの検索評価セット(約30本、両区分、言い換え・否定・経歴の言い方)を作り、上位3件の再現率をオフラインで測る
- 比べて選ぶもの: embedding のモデル・次元、下限と相対値の決め方、求人を embedding にする文面(注意点を入れるか など)。モデル名と料金は公式ドキュメントで確かめる
- dip のツールは「LLM を使わず、速く・事実だけを返す」方針のまま。問い合わせを LLM で言い換えて広げる案は採らない
- それでも否定の言い方が拾えなければ、求人の属性(人と話す度合い・体を使う度合い)を足すかを、評価の結果を見て別に判断する

### playbook
- 置き場は dip 側の `dip_mcp/playbooks/{区分}_{chat|voice}.md`。`get_counseling_playbook(track, channel)` で配る。未定の playbook は「区分を確かめる」ことを最初に書く
- 中身は「明らかにすること」と「掘り下げ方」。次に何を聞くかは決めない
  - 正社員: 目的・転職の理由 / 強み(履歴書と会話から本人の言葉で) / 次にやりたいこと・避けたいこと / 条件(年収・勤務地・働き方・時期) / 不安(ブランク・年齢・未経験職種への挑戦 など)
  - アルバイト: 目的(生活費・副業・経験・学業と両立 など) / 生活の制約(時間帯・曜日・エリア) / 興味・得意 / 経験 / 不安
- 区分に共通の決まり: 目的とやりたいことは最低1回掘り下げる。選択肢は履歴書と本人の発言から作り、一般論の例を使わない。「分からない」には職種の列挙でなく掘り下げに戻る
- 会話の決まりは区分ごと: 正社員は吹き出しの字数と「3回目の返信までに分岐」を緩める(値は実装タスクで決め、評価の形式判定も合わせる)。アルバイトは今のまま
- チャットと音声は同じ骨格で、言い回しだけ変える(音声は短く、1問ずつ)。v1 の Prompt の「相談モード」節は playbook に置き換える

### 保存とチャネル間の共有
- `save_user_preferences` は1つのまま項目を足す。共通: `purpose`・`strengths`・`wants`・`avoids`・`concerns`。正社員のみ: `min_annual_salary`・`work_style`・`start_timing`。本人の言葉のまま短い文で。電話番号・メール・住所らしい値を弾く防御は全項目に効かせる。jyoka/tasks#61(相談プロファイルの長期メモリ)はここに吸収する
- `record_conversation_outcome` に、200字以内の「相談のまとめ」を足す。本人の発言に基づく事実と、次に確かめることだけを書く
- チャットも音声も `get_user_conversation_summary` の同じ要約(区分・保存項目・相談のまとめ・履歴書)を読み、音声で話した内容も同じツールで保存する
- 評価の「聞き直し」の判定を、新しい項目にも広げる

### プロフィールの「すべて消す」の範囲(ユーザーの決定、2026-10-03)
- プロフィール画面の「すべて消す」は、その人の aica の中の記録を、**応募の記録も含めて全部**消す。消すもの:
  - 保存した希望(`save_user_preferences` の項目)
  - 相談のまとめ
  - 会話(LINE 側のチェックポイント)
  - トークを開いた記録(初回訪問か再訪かを決めるもの)
  - 雇用区分の切り替えの記録
  - 履歴書の読み取り結果
  - 音声の下書き(書き出したファイルも)
  - 保存した求人
  - 閲覧
  - 応募フォームの離脱
  - 応募
  - 連絡の記録
  - まだ届いていない変更の知らせ(`profile_changes`。次のターンで AI に渡すもの)
- 消した後は、次に開くと初回訪問として始まる
- 消さないのは、会話数の上限の数(quota)と費用台帳だけ。消すと上限を迂回できるため。費用台帳はトークン数と費用だけを持ち、発言の中身を持たない
- 実装: `line_runtime/server.py` の `/api/profile/forget` が、`dip_mcp/profile.py` の `forget_all`(`reset_user` でその人の dip の状態をまるごと初期化)と、会話のチェックポイントの削除を呼ぶ
- 同じブラウザ(同じ Cookie の匿名ID)の `/dev` のシナリオ利用者「匿名ID:シナリオユーザー」(例 `匿名ID:sim-new`。`/dev` のトークから入った音声相談の記録もここに入る)も、本人の記録なのでまとめて消す。評価シナリオ(`evals/scenarios.py` の `load_scenarios`)にあるシナリオユーザーごとに、上と同じ消し方(dip の状態・会話・読み取れなかった直前のアップロード(メモリ上の `unread_uploads`)・音声の下書きのファイル)をする。別のブラウザのシナリオ利用者は消せない(jyoka/tasks#122)。本番の `/` の音声相談は匿名ID そのもの(`w-…`)に入り、上の消し方で消える

### 音声の下書き
- 履歴書下書きのスキーマ(`docs/design/resume-draft-schema.md`)は1つのまま、任意項目 `document_kind`(履歴書 / 職務経歴書)を足して format_version 1.1 にする。任意項目なので、履歴書の読み取り(resume-intake)と保存はそのまま動く
- 正社員: 職歴ごとの成果と数字(規模・期間・結果)を掘り下げ、職務要約を整えて職務経歴書として出す。アルバイト: 今までどおり履歴書。未定: 最初に1問で区分を確かめる
- 「下書きを見る」の表示を、書類の種類に合わせて見出しと並びを変える

### 評価と予算
- ペルソナを5本前後足す: 経歴の厚い正社員志望(履歴書あり)/ 正社員だが副業でアルバイト / 学生の初めてのアルバイト / ブランクのある主婦・主夫 / 途中で「やっぱり正社員で」と切り替える人。全体で約14本
- 区分の切り替えは機械判定: 期待するターンで、期待する区分で `set_search_track` が呼ばれたか
- 深さは LLM ジャッジの評価項目: 目的を聞いたか / 目的かやりたいことを1回以上掘り下げたか / 選択肢が本人の履歴書・発言から作られているか / 提案理由が本人の話とつながっているか。それぞれ満たした・満たさないと根拠の発言
- 形式の機械判定(1問ずつ・80字など)は区分ごとに緩める
- 実 API の予算は **PRD 全体で $5**。エージェントは本番モデル、模擬ユーザーとジャッジは安いモデル(公式の料金表で確かめて選ぶ)。ターン上限(例: 8)と、シナリオを絞って回す指定(`--only`)を足す
- 回数: 基準の計測 全14本×2回、playbook の調整 相談・正社員の5本×最大5回、完了時の計測 全14本×2回(見込み約 $1.7)。各実装タスクの開発中・PR はオフラインの台本テストだけ(実 API 0回)
- 評価の実行ごとに費用台帳の累計を表示し、**累計 $4 に達したら止めてユーザーに相談する**
- 基準の計測のときに会話3本を人が読み、ジャッジの判定と照合する。合わなければジャッジだけ本番モデルに戻す(その場合も $5 に収まる見込み)
- 評価の差が小さいときは「差なし」と扱い、はっきり悪化したものだけを直す(2回ずつなので、ばらつきの判断は弱い)

## Testing Decisions

- 良いテストは、ユーザーから見える振る舞い(トーク画面の API から入って、返信・カード・dip の状態・要約に何が出るか)を確かめる。実装の内部(どの関数を何回呼んだか)をなぞらない
- 各実装タスクはオフラインの台本テスト(LLM を台本で差し替え、本物の dip MCP を通す)で確かめ、実 API を呼ばない。先行例: `tests/test_revisit.py`、`tests/test_consult.py`、`tests/voice/test_uploaded_resume.py`
- 区分の切り替え: 明示・強い合図・弱い合図・履歴書だけ・取り消し・再訪での引き継ぎを、台本でそれぞれ確かめる
- 保存と共有: チャットで保存した項目と相談のまとめが、音声のアドバイザーの指示に入ること(PR #10 の再現テストと同じ作り)
- 求人: 区分ごとの職種の完全一致、pay の表示、未定での両方からの提案、事実照合(fabrications)の pay 対応
- 検索: 検索評価セットの再現率をオフライン(求人ベクトルは固定ファイル、問い合わせのベクトルは記録したものを使う)で測る
- 評価の機械判定を足すときは、正しい振る舞いを違反にしない負例のテストを必ず添える(v1 で評価器の偽陽性を3回繰り返した反省)

## Out of Scope
