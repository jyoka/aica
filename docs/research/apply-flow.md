# 調査: 求人カード「応募」の先の設計(応募フロー)

2026-09-27。jyoka/tasks#66(親: #54 PRD AICA v1)の調査レポート。コードは書かない。
求人カードに「応募」ボタンを付けるとき、その先をどう設計するとユーザーにとって一番楽で、応募意欲が上がるかを比較し、推奨案と issue 分割案を出す。

## 1. 前提(いまの aica / line-sim の状態)

参照したコードは line-sim コア(#55 で移植されるもの)。task/55 時点のパスで書く。

| 事実 | 場所 |

### B-exit(応募フォームの途中離脱)シナリオの知見

`docs/design/line-sim-scenarios.md` の 4・5 番と evals から。

- 離脱理由として設計上いちばん重いのは「入力が面倒だった」。次に「仕事内容が不安」「条件が合わなかった」。つまり離脱対策は (a) 入力項目を減らす、(b) 不安への質問にその場で答える、の2本柱になる。
- 途中まで入れた内容は捨てずに「残りだけ」を案内すると support の出口に到達できる(残り2項目: 電話番号・希望開始日、のような形)。
- ユーザーは PII をトークに書いてしまう(`pii` シナリオ)。受け取らずに画面へ案内する動きは実装・評価済みで、応募フローもこの前提を壊してはいけない。
- 「やめた」と言う人には理由を聞かずに静かに終える。応募フローでも離脱者を追い回さない。

### 外部の一般知見(出典は末尾)

- Web の応募フォームは開始者の 60-75% が完了前に離脱する。長いフォームは 80% に近づく。
- 設問数と完了率は強い負の相関。必須・任意の混在配置も離脱を増やす(EFO の定番知見)。
- 会話形式(1問ずつ聞くチャット)の応募は完了率 90% 前後の事例が複数報告されている(58%→89% になった外食チェーンの事例など)。
- LINE 上で応募まで完結する手軽さは応募数を押し上げる(タウンワークの LINE 活用で応募件数約80%増の事例)。

aica の会話骨格(1返信1質問・クイックリプライ)は、この「会話形式が完了率で勝つ」条件をすでに満たしている。

## 2. 比較する4案

応募に最低限必要な項目を「非PII(希望開始日・シフト希望など)+ PII(氏名・電話番号など連絡先)」と置いて比べる。

- **案A: トーク完結型** - 応募ボタンを押すと AI が全項目(PII 含む)をトークで1問ずつ聞き、トーク内で応募確定まで終える。
- **案B: トーク主導ハイブリッド型** - 非PII はトークのクイックリプライで聞き、PII だけ専用画面(旧 LIFF 相当、既存 `/liff/apply`)の最小フォームで入力して確定。完了はトークに戻して伝える。
- **案C: 専用画面一括型** - 応募ボタンを押すと即座に専用画面へ飛び、全項目をフォームで入力する。トークは入口だけ。
- **案D: 外部フォーム誘導型** - 応募ボタンは外部(求人媒体・店舗側)のフォームへのリンク。aica は何も預からない。

その他に検討した派生: **案E: 2回目以降のワンタップ応募**(初回に専用画面で入れた PII を dip 側に応募プロファイルとして保存し、2回目からは「前回の内容で応募しますか?」の確認1タップ)。これは案B・Cの上に載る追加であり、単独案ではないので追補として扱う(6章)。

## 4. 推奨案: 案B(トーク主導ハイブリッド型)

### 流れ(たたき台)

1. 求人カードに「応募する」ボタンを追加(既存の「詳しく見る / 保存」の並び)。
2. タップすると dip 側に応募ドラフト(既存 `form_exits` と同じ形: completed / remaining)を作り、AI が非PII の残り項目をトークで1問ずつ聞く。クイックリプライで答えられる形にする(例: 希望開始日 → 「今週中 / 来週から / 相談したい」)。上限2-3問。不安や質問が来たら `answer_job_question` で先に答える。
3. 非PII が埋まったら「あと〇項目(氏名・電話番号)だけ画面で入力して完了です」と残り数を明示して `/liff/apply` のボタンを出す。
4. 画面は PII のみの最小フォーム。入力済み項目を上部に表示(すでに実装あり)。送信で `submit_application`、完了ページ+トークに完了メッセージを返す。
5. 途中で止まったら応募ドラフトがそのまま B-exit 状態になり、既存の「続きから」案内が安全網になる。v1 はプッシュが無いので、拾い直しは再訪イベント時に `form_exit` を確認して1回だけ声をかける形にする。

### 理由

- **手間が最小の構成**: 会話形式が完了率で勝つという外部知見と、B-exit の「入力が面倒」が最大離脱要因という内部設計の両方に対して、「タップで済むものはトークで、手入力が要る PII だけ最小フォームで」が最短。画面側の B-exit 面積(フォーム項目数)を構造的に最小化する。
- **確立済みの安全設計を壊さない**: 案A だけが PII ガードレールの撤廃を要求する。`pii` 評価シナリオ・プロンプト・`PII_VALUE` 拒否は aica の信頼の柱(PRD US22)であり、応募のために捨てるのは本末転倒。
- **実装の8割が既にある**: resume フロー・専用画面・ボタンの `/liff/` 制限・PII 拒否は動いていて評価済み。新規はカードのボタン、ドラフト作成ツール、完了のトーク反映くらい。
- **応募意欲の設計に合う**: 応募直前の不安(B-exit の第2の離脱理由)にトーク内で答えてから画面へ送れる。完了がトークに戻るので「応募して終わり」でなく関係が続き、選考連絡の不安対応(既存 support)にもつながる。
- **v1(架空求人・知人テスト)でテスト価値が出る**: 案D は飛び先が無く体験を測れない。案B なら「応募開始→完了」のファネルをログで測れて、知人テストのフィードバック対象になる。

### 案Bの弱点と手当て

- 唯一の断絶点はトーク→画面の切り替え。ボタンの文言で残り項目数を明示する(「あと2項目だけ入力して応募する」)、画面側に入力済みを見せる、完了後の戻り導線を必ず出す、の3点で削る。
- トークでの質問が続くと「質問攻め」になる。非PII の質問は2-3問を上限にし、既に長期メモリ・相談プロファイルにある値(希望開始日など)は聞かずに確認だけにする。
- 応募を迫らない原則との両立: 応募ボタンはユーザー発なので原則と矛盾しないが、AI 側から「応募しませんか」と誘導しない現行ルールは維持する。

## 5. 推奨案の issue 分割案(たたき台)

依存順。1つずつ独立に PR にできる縦切り。

1. **応募ドラフトの作成とトークでの非PII 収集** - 求人カードに「応募する」ボタンを追加。押すと dip 側ツール `start_application`(仮)が `form_exits` と同形のドラフトを作り、AI が非PII の残り項目をクイックリプライで聞いて `resume_application_form` で埋める。プロンプトに応募ステージの指針を1節足す。オフライン台本テスト付き。
2. **専用画面の新規応募対応と完了のトーク反映** - `/liff/apply` を「B-exit の続き」専用から新規応募ドラフトにも対応させ、PII のみの最小フォームにする(残り数・入力済みの表示は流用)。送信後、トーク側に応募完了メッセージと次の選択肢(「応募履歴を確認 / 求人を探す / 今はいい」)を出す。
3. **途中離脱の拾い直し(B-exit の v1 再配線)** - プッシュ削除後の v1 で、再訪イベント時に `form_exit` を確認して1回だけ続きを案内する。「やめた」と言われたら静かに引く既存の振る舞いを踏襲。B-exit・pii 評価シナリオのトリガーを再訪起点に書き換える。
4. **応募フローの評価シナリオとファネル計測** - 新規応募の happy path / 応募途中で質問して戻る / 応募途中に PII をトークに書く、の3シナリオを evals に追加。checks に「応募を AI 側から迫らない」「PII 項目をトークで聞かない」を足す。応募開始→画面到達→完了をログ(費用台帳と同じ台帳形式)で数え、知人テストのファネルを見られるようにする。
5. **(follow-up・任意)2回目以降のワンタップ応募(案E)** - 初回応募の PII を dip 側の応募プロファイルに保存し、2回目からは「前回の内容で応募しますか?」の確認だけにする。実 PII を預かる話になるので、知人テストの範囲では架空値前提の動作確認に留め、保存の要否・期間・削除導線を issue 内で先に決める。

## 6. 追補: 案E(ワンタップ応募)を最初からやらない理由

Indeed の Easy Apply 型は手間の理論最小値だが、v1 で最初からやらないのは (a) PII の永続化という新しい約束(保存範囲・削除・漏えい時の説明)を知人テスト前に背負う必要がある、(b) 履歴書アップロードの PII は保存しない、という PRD の既決(US21)と整合を取る設計判断が要る、(c) 初回応募の体験(案B)が先に無いと乗る土台が無い、の3点。案B のファネル計測で「画面での PII 入力」が実際に離脱点になっているとデータで見えてから、issue 5 として着手するのが順当。
